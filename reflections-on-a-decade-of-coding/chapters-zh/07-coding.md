# 写代码（Coding）

原文：<https://www.scattered-thoughts.net/writing/coding/>  
发布日期：2021-12-20

*本文是系列文章中的一篇，系列从[《十年编程生涯的反思》](00-reflections-on-a-decade-of-coding.md)开始。*

这一篇会比本系列其它部分含糊得多，因为它讲的是真正的工作本身。好的判断力是从经验里学来的，不是从博客文章里学来的。所以我认为，我能传达的最有用的东西，是我在写代码时会考虑哪些方面，而不是我得出的那些答案。

我也尽量把重点放在那些对我而言并非显而易见、或者与我受到的教导相悖的事情上。

---

我脑子里放在第一位的是这个想法：写程序的目标，是把输入变成输出，同时把有限的人力和机器资源用好。

---

目标不是写出漂亮的、优雅的、或者读起来像英语一样的代码。

我当然想写可读的代码，但我读代码，是因为我想知道代码实际做了什么，而不是它声称自己做了什么。

这包括理解它读了或写了哪些数据，以什么顺序、在什么时间。所以我最终形成了一种有点“粗野主义”（brutalist）的审美：数据完全摊在明面上，对数据的访问也不会被藏在一层层方法调用和私有字段后面。

我发现，这种以数据为中心的做法对我处理的那类问题非常有效；但我也在许多其它领域看到有人提倡这种做法，例如：

- [底层、受性能约束的系统](https://www.youtube.com/watch?v=rX0ItVEVjHc)
- [高层、长期存活的系统](https://youtu.be/2V1FtfBDsLU?t=642)
- [分布式系统](https://www.youtube.com/watch?v=R2Aa4PivG0g)
- [增量式编译器](https://vimeo.com/649009599)与 [IDE 工具](https://www.youtube.com/watch?v=_muY4HjSqVw)

这种做法与编程通常被教授的方式截然相反——后者要求在每一个微小的边界上都施加最大限度的防御性封装，并尽可能把数据藏在不可透视的接口后面。用这种风格写出来的代码，要回答“在 myobj.bar() 内部调用 myobj.foo() 是否安全”或者“在哪些时间点上，quux 的值与上游 baz 的值是同步的”这类问题，就变得非常困难。它还往往产出“一次一个对象”、大量复制的 api，妨碍我们高效地利用硬件。

---

最根本的设计问题始终是“我想让机器做什么”。其它一切都只是简洁表达那种行为的工具。所以当我在决定怎么设计 schema、或者怎么把代码组织成模块等等时，唯一要紧的是：什么最有助于让计算机做那件事。

如果我发现自己开始思考“承包商是否‘真的’算一种雇员”，或者“两个函数是否‘属于’一起”，那就是掉进陷阱了。试图让代码正确地映射现实的结构，是没意义的，因为那个结构并不存在。这些分类[存在于我们头脑里](https://www.lesswrong.com/posts/yA4gF5KrboK2m2Xu7/how-an-algorithm-feels-from-inside)，而不在世界里；它们只有在有用这个意义上，才算得上“正确”。

真正要紧的是关于机器行为的问题——比如：我们是否应该像对雇员那样，从支付给承包商的款项中代扣税款？或者是否要把承包商排进强制性的员工培训？一旦你得到了所有这类问题的答案，那么在承包商与雇员被同等对待的所有情形里，这段代码你只需写一次；而在其它所有情形里，你必须写不一样的代码。到这一步，“承包商是否‘真的’算一种雇员”这个剩下的问题就是空洞而无意义的了——没有任何经验性的检验能回答它；即使有，那个答案对程序的设计也不会有任何影响。

---

这个陷阱的一个特例，是试图把所有东西都组织进某种层级结构里。任何代码组织工具的用意，都是捕捉期望行为中的重复模式，好让我们不必把同一件事写成成千上万个略有不同的版本。但没有任何法则规定这些模式必须是树形的。有时候，有用的分类会互相交叠。硬要把问题的结构塞进某种类层级里，不过是自找麻烦。

把代码组织进文件和文件夹也是如此。总是存在不同的横切关注点，暗示着不同的树形组织方式。为找出那个“正确”的分法而浪费大量时间，真的不值得。

## 逻辑设计

我通常先从数据开始思考，把数据看成原子事实（atomic fact）。

事实是那些将始终为真的事情。所以“Bob 是承包商”不是一个事实，但“Bob 于 2021-11-10 与我们签署了一份承包协议”是。

如果在这件事上想得太深，你最终会撞上“无法直接触及客观现实”这堵墙。所以别想太深——某个东西只要对这个程序而言“始终为真”就够了，也就是说：我们的代码永远不需要删除或修改它。

同样，“原子”意味着：对这个程序而言，整个事实要么一次性全部被输入／计算出来，要么就完全没有。所以“Bob 从 2021-11-10 到 2022-11-10 期间有一份承包协议”可能是原子的——如果你总是使用带固定结束日期的合同；但若非如此，它可能需要拆成“Bob 于 2021-11-10 签署了合同 1047”和“Bob 于 2022-11-10 终止了合同 1047”。

---

上面突然冒出来的“合同 1047”是很典型的。如果你对某个东西该知道的一切全都已经知道，那以后你就可以用那一整组事实来指代它（现实一点说，是用那组事实的哈希值）。但如果信息是随时间一点点渗进来的，那你就需要找到或创建一个 id，把这些事实拴在一起。

最容易的做法，是在这个对象第一次被提及的时候，生成一个顺序的或随机的 id。于是某人点击“新建合同”，我们报告说新合同的 id 是 1047。此后任何输入都必须带上这个合同 id。实际上，我们把这个合同相关事实的“拴在一起”问题甩给了外部世界——它以后与我们的系统交互时，必须记住这个合同 id。我们同样可以把随机 id 换成“用户 X 在时刻 T 创建的合同”。

只有在“新建合同”是一个唯一事件时，生成 id 才管用。如果从点击“新建合同”到分配合同 id 之间还存在可能失败的操作，那我们重试某个操作时就可能不小心分配出多个 id。所以我们希望把 id 的分配尽量贴近引发它的那个事件：比如，如果是在浏览器里点“新建合同”按钮，那我们就应该在浏览器里分配一次 id，然后（可能重试着）把它提交给服务器。

（在系统边缘生成 id 的另一个原因是：如果一个系统在输入相同时却生成不同的 id，那很难为它写测试——把 id 直接放进输入里就容易得多，这样测试的输出可以是确定性的。）

在处理增量维护或缓存时，我们还必须考虑：相对于输入的常见变化，id 与缓存数据之间的关联有多稳定。例如在 IDE 里，我们不会想用“从第 172 个字符开始的变量”作为 id 来缓存类型信息，因为该文件里任何一次插入或删除，都会要求改动大部分缓存数据。相反，我们可能想用类似“名为 bar 的第一个函数里名为 foo 的第一个变量”这样的东西，它只在函数名或变量名被编辑时才会变化。

许多数据建模方法要求你先在世界上识别出“对象”或“实体”，但一旦深究，“身份”这件事在哲学上就变得麻烦起来。我发现，从期望的行为开始容易得多，然后再从我想要连接的事实、或者我想要缓存的计算中推导出 id。

---

接下来我思考如何把输入变成输出，以及什么中间状态对写这段代码有帮助。最后我得到某种数据图：输入在顶部，输出在底部，中间是各种派生数据。

理想情况下，我还想对数据有某种量化的理解——有多少输入、它们如何分布、数据里是否存在很强的相关性，等等。但在做数据库引擎时，答案通常是“尽可能多”，所以我只能退而求其次：去看现有的基准测试和案例研究，并试着同时给出下界和志向性的目标。

---

当我把这些明确讲出来时，听起来像是一个极其正式、繁复的过程，但它大部分是自动发生的。除非我在为某个困难或庞大的问题做前期设计，否则它通常不过是笔记本上的几笔乱写和草图，而且很多时候我根本不必有意识地去想它。

## 物理设计

那么现在，我必须把这个设计映射到一台真实的机器上。数据图告诉我我想计算什么，但我仍然需要考虑：

- 是存储输入，还是只存下游的中间状态
- 是存储中间状态，还是从头重算它
- 如何在内存中和磁盘上安排数据
- 以什么顺序计算中间状态／输出

关于如何做这些决定，我其实没有什么建议可给。我不知道有哪本书、哪门课或别的什么，能把这方面教好。我知道很多教得糟糕的。

[《Data-Oriented Design》](https://www.dataorienteddesign.com/dodbook/)不算差，但它主要提供的是工具，而不是解释该如何、何时使用它们。

---

就学习如何写出快的软件而言，我找到的最好的资源，是去看那些性能远超出既有预期的项目（比如 [redpanda](https://vectorized.io/blog/fast-and-safe/)、[sorbet](https://sorbet.org/docs/talks/jvm-ls-2019)、[zig](https://vimeo.com/649009599)），并试着理解它们的不同之处在哪里。

---

对于键值或有序数据结构，[RUM 假说](https://dl.acm.org/doi/pdf/10.1145/2882903.2912569)是一个非常有用的组织原则。基本内容是：你在乎读性能、写性能和空间占用这三件事。它们似乎天生互相拉扯——某个数据结构在一条轴上占便宜，往往是以在另一条轴上吃亏为代价。

给它“作弊”的一个办法是：对数据的不同子集选择不同的取舍。比如把热数据存在写优化的结构里，把冷数据存在读优化的结构里。或者把操作批量化，这样你可以先做完所有写操作，再为后续步骤产出一个读优化的结构。

---

很多 bug 都源自：把同一份状态的不同表示都存下来，然后它们彼此之间失去了同步。

避免这点最容易的办法，是只保留一个唯一可信来源（single source of truth），每次从头重算下游状态，而不是把它存起来。

如果出于性能原因这不可行，那我就尽量让“意外访问到过期状态”变得不可能，通常通过以下两种方式之一：

- 强制所有对上游状态的写入都必须经过某个 api，而这个 api 同时也会删除或更新下游状态
- 用时间戳／版本号／输入哈希给下游状态做键，然后在读取时检查这个值是否已过期

我强烈怀疑，像 [salsa](https://github.com/salsa-rs/salsa) 这类更系统化的方法有很大的潜在收益，但我自己还没有在任何生产软件里试过这类技术。

## 代码

一旦数据的结构和流动被弄清楚，写代码就没那么复杂了。把必须发生的所有事情按正确的顺序写下来。如果有一组值总是被一起传来传去，就把它们归成一个 struct／对象。如果代码里有大量重复的结构，就试着把它挪进一个函数里。如果为了减少某个特定的重复结构，结果反而把事情弄得更复杂，那就干脆接受这点重复。

[语义压缩](https://caseymuratori.com/blog_0015)把这个过程描述得相当好。

---

我目前写下的所有内容，都要求我对自己想解决的问题的细节做大量思考。由此立刻得出的一条推论是：不要试图为那些我并没有打算解决的问题写代码，因为那些细节我一无所知。

这几乎与我早期学到的所有东西都相反——那时讲的全是如何让解决方案尽可能通用。实质上，我被教导的“解决问题的正确方法”，是先把这个问题替换成一个更困难、而我信息更少的问题。事后看来，这不太明智。

---

在代码结构方面，我主要考虑的是：后来的人怎样才能理解它。这包括能读懂并理解代码本身，也包括运行时的可观测性和调试。

让阅读变困难的东西包括：间接层、回调、宏、异常，以及任何会破坏“跳到定义”的语言特性。

让可观测性变困难的东西包括：过度的数据封装／隐藏，以及像不透明闭包（opaque closure）这类隐式的、难以查询的状态。

---

我倾向于[写更长的函数](http://number-none.com/blow/john_carmack_on_inlined_code.html)。我发现读一个长函数，比在一棵由短函数组成的树里跳来跳去更容易。

如果存在大量向后跳转或深度嵌套的控制流，我更可能把它拆开，因为那和多函数之间跳转一样难以阅读。理想情况下，我会把所有复杂的控制流塞进代码的“一页”里，而把其余逻辑放进只向前推进的函数里。

为了让高层结构更便于快速浏览，我尽可能把临时变量藏在一个块（block）内部。

``` language-zig
// Need to check any pending timestamp that is before the new input frontier
var timestamps_to_check = u.ArrayList(Timestamp).init(self.allocator); // <-- this is used later in the function
{
    var timestamp_iter = timestamps.iterator(); // <-- this is only used inside this block
    while (timestamp_iter.next()) |timestamp_entry| {
        const timestamp = timestamp_entry.key_ptr.*;
        if (input_frontier.frontier.causalOrder(timestamp) == .gt) {
            try timestamps_to_check.append(try u.deepClone(timestamp, self.allocator));
            try frontier_support_changes.append(.{ .timestamp = timestamp, .diff = -1 });
        }
    }
}
```

大多数块都会配一句简短的注释，说明它们的用途，这样读者可以快速浏览、把握整体结构。

在做棘手的东西时，我会先把块注释写出来，然后才往里填代码。这有助于我记住接下来要做什么。

---

在单个文件内，你可以按合乎逻辑的顺序依次引入东西。如果同一段代码被拆散在许多小文件里，这种上下文就丢失了。所以我倾向于用更大的文件。

---

我喜欢把程序里的所有状态组织成可以从某个根指针抵达的形式。

这样一来，读者只要顺着类型构成的树往下走，就能轻松理解程序分配的所有资源。

它也让“在调试器里找到任何一处状态”变得容易，或者方便写一些小小的调试辅助工具，比如检查全局不变量、打印队列长度。

``` language-zig
pub fn main() void {
    var state = State.init();
    while (getEvents()) |events| {
      handleEvents(&state, events);
      // put debugging stuff in here
    }
}
```

这并不意味着每一段代码都能访问所有状态——每个组件在调用其子组件时，只把子组件需要的那部分状态传进去，所以我们仍然可以单独测试各个组件。但临时插入的调试代码可以触达一切。

---

我尽可能把状态做成树形。

一旦你允许指针在不同组件之间互相指向，以下这些事就变得更难了：

- 推理一个函数依赖或可能改动哪些状态，因为它总能找到一条通往其余“丛林”的指针
- 测试或复用组件，因为这些组件要求那些指针指向的目标都存在，于是你为了运行一个组件，不得不造出整个状态的假版本
- 打印、检查或复制状态，因为指针图里可能存在环

在非托管语言里，还有一个额外的麻烦：任何被指针指向的东西都不能被移动。这限制了你保持内存布局紧凑的选择余地，也往往会引发微妙而耗时的 bug。

关于如何避免组件之间的指针，可参见[《Handles are the better pointers》](https://floooh.github.io/2018/06/17/handles-vs-pointers.html)或[《Data-Oriented Design》](https://www.dataorienteddesign.com/dodbook/)。

---

我也尽量让对状态的访问沿着树向下流动。

我的意思是：一个正在访问状态中某一部分的函数，可以调用那些访问该部分子节点的函数，但不允许调用访问其兄弟节点或父节点的函数。

这样做的原因是：在函数内部，经常需要临时打破某个不变量、或者处于某种奇怪的中间状态。当控制流成环时，最后会发生的情况是：`foo(A)` 调用 `bar(B)`，`bar` 又调用 `quux(A)`，而 `quux` 假设 `A` 上满足某些不变量——可这些不变量正被 `foo` 临时打破了。

要强制执行这一点并不总是合理的。例如在 [focus](https://github.com/jamii/focus) 里，每个 buffer 可以有多个 editor，而每个 editor 又可以有多个光标。当在一个光标处插入一个字符时，所有其它 editor 里所有其它光标的位置都需要更新，而且必须在其它任何东西访问这些光标之前完成。有办法避免立刻做这件事，但这些办法看起来都比“允许 buffer [反向够回](https://github.com/jamii/focus/blob/4f937d0d82b73f5ecbbdc17ad967a7d46e814a5a/lib/focus/buffer.zig#L360-L362)它所挂接的 editor”更容易出错。

---

状态通常伴随着一些不变量：代码可以依赖它们，也被期望维持它们。在注释里解释这些不变量是个起点；但最近我还会加上一些函数来检查这些不变量、并报告任何违反，然后在整个代码的关键位置撒上一些只在 debug 构建里启用的调用。

这往往能缩短调试时间，因为它指出的是事情最初出错的地方，而不是症状最先显现的地方。

---

我现在真的很讨厌回调。

不是指那种立即调用的，比如 `list_of_things.map(thing => ...)`。这类没问题，因为读代码时我能确切说出会发生什么、什么时候发生。

但那些会被存到某个地方、也许稍后才运行的回调，比如 `thing.on_event(event => ...)`，就是邪恶的。因为以后我读代码时，看到 `thing.on_event` 被触发，接下来可能发生什么？字面意义上的任何事——取决于代码库中任何位置上、任何时间点上，是否注册过回调。

回调本身也得面对类似的问题。回调可能在任何时间点被执行，所以无论程序其余部分处于什么状态，它都必须能被安全地运行。

（我觉得值得注意的是，很多前端模式最终都收敛成 `thing.on_event(event => queue.push(event))` 这样的回调。把一个事件入队、稍后再处理，是唯一一个永远安全的动作。）

调试时，我想理解系统的状态。如果系统里到处是回调，那系统的状态永远是“一串不透明闭包”。大多数运行时甚至不让你看到这串东西，于是你连“这个程序是在等某个 IO、还是已经无事可做”都问不出来。

同样的论证适用于大多数 async/await 的实现，它们把你的整个程序变成一串不透明闭包。也许我们最终会有能理解 async/await 的调试器和性能剖析器，但在那之前，这是个不小的负担。

其中一个特例，是那些入口长得像这样的框架：

``` language-zig
thing.run(event => logic(event))
```

这种风格的 api 不仅有上面所有的问题，还把自己所有的状态藏了起来，并且假定它是你程序里唯一的事件循环。我总是更喜欢这样的 api：

``` language-zig
var thing = Thing.init();
while (thing.nextEvent()) |event| {
  myEventHandler(thing, event);
}
```

bitsquid 博客的[这篇文章](https://bitsquid.blogspot.com/2011/02/managing-decoupling-part-2-polling.html)里有各种避免回调的思路。

---

有一个常见的论点：开发者的生产力比性能更重要。把这个论点推到极端，人们常常用它来为“把系统实现得很糟、然后靠把它分散到多台机器上、和／或在前面加一层缓存来弥补”辩护。考虑到分布式一致性和缓存失效是软件工程中最难的两个问题，这看起来适得其反。

人们通常想当然地认为：更好的性能必然要求更高的复杂度。但我常常有这样的经验：把系统中某个组件做快，反而能让整个系统更简单——比如因此不再需要水平扩展或下游缓存。

---

改进性能的典型做法是：先把软件随便写出来，然后做性能剖析，试着优化热点。

但每当我遇到真正快的软件，作者都不是靠在某个热点里塞进聪明的代码做到的，而是靠精心设计整体架构、把硬件用好。一旦架构定下来，想纠正大尺度的错误就太晚了。

把架构做对的方法，是一开始就利用关于这个问题、输入数据以及硬件能力的知识，估算出一个粗略的性能上界，然后把性能度量成“理论最大值的一个百分比”。

这并不意味着我必须努力达到那个理论最大值，但至少每当我做出一个偏离它的决定时，我是知道的。

例如，[simdjson](https://github.com/simdjson/simdjson) 能以每秒几 GB 的速度解析 json。这算快吗？谁知道呢。

但[他们的论文](https://arxiv.org/pdf/1902.08318.pdf)用“每字节消耗多少 cpu 周期”来度量解析的每一个阶段。既然我们知道 cpu 上有哪些指令可用、每条指令要花多少周期，这就能给出一个粗略的上界，并告诉我们：在同一套硬件上，如果不做多线程、或者不[改变问题的定义](https://simdjson.org/api/0.6.0/md_doc_ondemand.html)，我们不太可能再挤出另一个数量级的提升。

---

如果信息集中在一处，就更容易理解某个东西是怎么工作的。

例如，在 materialize 里，启动所有组件并把它们粘合在一起的代码全在[一个函数](https://github.com/MaterializeInc/materialize/blob/e1528979bc4e9d14aca7da3db804aaa2e5bff370/src/materialized/src/lib.rs#L175-L330)里。你读这几百行代码，就能理解哪些组件之间可以通信、以及是怎么通信的。

一个做错的例子就在我的文本编辑器里：editor 组件有[好几个函数](https://github.com/jamii/focus/blob/62abfa893260001514645d40e0da560d040ddd76/lib/focus/editor.zig#L1189-L1207)用来滚动视口，而它们从许多不同的地方被调用，比如光标移动了、窗口尺寸变了、或者 buffer 的内容被别处改动了。

如果在同一帧里有好几个不同组件都想滚动视口，会发生什么？这取决于这些调用的发生顺序，而顺序又可能取决于不同窗口被打开的先后，或者仅仅因为我重整了某段不相关的代码就被意外改变了。这成了 bug 的长期来源。

更好的做法会是：把每一个“移动滚动位置”的请求追加到某个列表里，然后让代码里唯一的一处地方每帧查看一遍这个列表，决定优先满足哪个请求。

---

要让非确定性的软件正确，真的很难。

有些不确定性来源是问题固有的（比如网络通信），你最多只能把它们隔离到系统的边缘，这样至少你能确定性地重放捕获下来的历史。尤其是超时（timeout），最好留在边缘：比如定期向系统发送 tick 事件，而不是允许某些内部代码去查当前时间。

其它来源往往可以避免，比如给随机数使用种子（并使用可分裂的生成器，这样随机地重整代码不会改变结果），在多线程计算中使用确定性的构建块（[例如](https://arxiv.org/pdf/1901.01930.pdf)）。

把 IO 留在边缘也很有用，这样它可以被测试或重放。做法有很多种，而其中大多数我都没试过。
