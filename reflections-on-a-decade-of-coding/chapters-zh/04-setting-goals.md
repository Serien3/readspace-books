# 设定目标（Setting goals）

原文：<https://www.scattered-thoughts.net/writing/setting-goals/>  
发布日期：2021-10-06

*本文是系列文章中的一篇，系列从[《十年编程生涯的反思》](00-reflections-on-a-decade-of-coding.md)开始。*

如果我不知道自己想去哪里，通常也就到不了那里。

为每个项目设定明确的目标，对以下这些事至关重要：

- [衡量进展](04-setting-goals.md#衡量进展)
- [确定行动优先级](04-setting-goals.md#确定行动优先级)
- [做出取舍](04-setting-goals.md#做出取舍)
- [避免漂移](04-setting-goals.md#避免漂移)
- [避免争论](04-setting-goals.md#避免争论)

在设定目标时，我发现当目标具备以下性质时，效果更好：

- [诚实](04-setting-goals.md#诚实)
- [恒定](04-setting-goals.md#恒定)
- [详尽](04-setting-goals.md#详尽)
- [可证伪](04-setting-goals.md#可证伪)
- [渐进](04-setting-goals.md#渐进)

## 目标对以下这些事至关重要……

### 衡量进展

要想感觉自己正在取得进展，我需要知道自己正在朝什么方向进展，以及如何度量它。

有清晰的目标时，我能看到自己每天的努力如何把我推得离那个目标更近。子目标提供了里程碑，也提供了一种完成感——那种棘轮式一格一格向前的感觉。

没有清晰的目标时，我感觉自己在原地打转。我会不停地推翻又重做各种决定。我会士气低落，也很难继续往项目中投入努力。

**例子**：在 [strucjure](https://github.com/jamii/strucjure) 里，我隐约觉得模式匹配、解析、校验、ast 遍历等等都模模糊糊地相似，应该能被统一起来。但我既没有想解决的具体问题，也没有想回答的具体疑问——完全没有可以牵引进展方向的梯度。于是我把大量时间花在尝试不同的设计和 api 上，却没有任何标准来在它们之间做取舍，也没有标准告诉我什么时候算做完。

### 确定行动优先级

在任何项目上，我想做的事从来都做不完。有清晰的目标，才有可能按“每一项能把我朝目标推进多少”来给待办清单排序。

**例子**：对我的[文本编辑器](https://github.com/jamii/focus)来说，唯一的度量指标就是我自己的效率。所以对待办清单上的每一项，我都能估算它每周替我省下多少时间、相对于实现它需要多久，然后按投资回报率（ROI）给待办清单排序。

好的优先级排序意味着更快的进展，以及在“做决定”和“推翻决定”上花更少的时间，这两点都有利于保持动力。

### 做出取舍

人们谈起编程时，常常像是有一种通常正确的做法；但实际上，大多数决策都有许多合理选项，每个选项各有不同的取舍。除非我已经有一个详尽的目标可以用来评估这些取舍，否则这些选择会让人动弹不得。

我常常发现，这些选项没有一个对我的目标有多大影响——也就是说，我其实是在为一个无关紧要的决定痛苦纠结。

**例子**：在我早期的许多项目里，我花了很多时间为“如何把代码分到不同文件里”而纠结。后来我注意到，各种可能的分法，对我的代码维护能力其实都没有多大影响——更不用说赢回我反复斟酌所耗掉的时间了。所以现在，我倾向于把所有东西都放进一个大文件；等到它大到让我找不到东西了，我就随便挑一种拆法，不再多想。

另一些时候，我会意识到自己无法做决定，因为我没有足够的信息来评估它对目标的影响。这时我要么去别处找这些信息，要么就把多个选项各做一个原型，直接检验其影响。

**例子**：现代数据库要么把查询编译成原生代码，要么使用向量化的解释器。[imp](https://github.com/jamii/imp) 该选哪一种？已经有很多人研究过其中的取舍（[例如这篇](http://www.vldb.org/pvldb/vol11/p2209-kersten.pdf)），而答案似乎很大程度上取决于工作负载。所以与其现在做决定，我得先写更多、更大的 imp 程序，好让我更好地刻画这个工作负载。

### 避免漂移

把目标写下来很重要，否则它们会随时间悄悄漂移，而没有人察觉到。

当这种漂移表现为：在现有目标尚未达成之前就扩大项目范围，它的危害尤其大。

**例子**：一位朋友抱怨说，几乎没有哪个编辑器适合用来编辑大文件（大于 1gb、没有换行）。我很有把握在 [focus](https://github.com/jamii/focus) 里解决它，并对这个挑战兴奋起来。我在这上面大概花了 50–100 小时，差不多相当于我在编辑器其余部分投入时间的总和。我推进得相当远——能够加载并编辑 1gb 压缩过的 javascript——但仍然有一大堆 bug 要抓，还有棘手的使用体验问题要解决（例如在大文件里，搜索无法再在 UI 线程里同步执行）。我的速度慢了下来，最后完全停下了这项工作。终于，我意识到自己之所以失去动力，是因为我在勉力完成一个实际上根本用不到、也不在我原计划里的功能。我把整个分支丢掉，然后立刻又开始对做这个编辑器感到兴奋了。

我注意到，漂移特别容易发生在“替代目标”上——那些比原目标更有趣、更快给出回报的目标，或者那些能让人避开某些不快工作的目标。例如：写一个很酷的库去解决我这个问题的某个泛化版本，而不是直接解决这个问题。

漂移也会以“忙活”的形式出现——那些容易、有满足感、但优先级其实并不高的事。例如没完没了地重整代码让它“更好看”，或者为了把那些其实根本不需要测试的简单代码刷到 100% 覆盖率。

随着新信息出现而改变目标，这没问题；但把目标写下来，意味着这种改变是一次有意识的行动，而不是一场渐渐发生的意外。

### 避免争论

在团队中工作时，对于接下来该做什么、或者某件事该怎么做，分歧是免不了的，有时还会争得很凶。把事情回接到最初的目标上会有帮助，因为它能澄清：我们究竟是对于“目标应该是什么”有分歧，还是对于“某个行动会如何影响那些目标”的预测有分歧。

关于预测的分歧往往比较容易解决，做点调研或者做个快速实验即可。如果我们得不到确切答案，或许可以约定先按某一种做法试一段时间，然后再安排一次复盘。有时我们对影响是正面还是负面意见不一，但双方都意识到谁都不认为这个影响会很大，那么无论选哪种，大概都不值得为此争论。

关于目标的分歧可能难以化解，但至少如果目标已经白纸黑字写下来了，我们就能把分歧限定在某场元层面的讨论里，而不至于让其它每个议题都陷在泥里。理想情况下，每个人都足够专业，会同意在此期间朝同一个方向用力。（如果他们做不到，我也没什么洞见可给，只能祝你有位好主管。）

**例子**：这份 [rustacean principles](https://smallcultfollowing.com/babysteps/blog/2021/09/08/rustacean-principles/) 就是一次尝试，把 rust 项目的目标和价值观明确写出来，用以引导关于新特性的讨论。

## 目标在具备以下性质时效果更好……

### 诚实

有时候，我写下的并不是自己真正的目标，而是不知不觉写下我*认为应该*是我的目标。于是我发现自己扭曲成各种形状，试图用“我说我想做的事”来为我“实际想做的事”辩护。

有时候，原因是某种同侪压力：我写下的是“一个优秀工程师™”应该在意的东西。或者，我会发现自己试图用别人看重的东西来为我在做的事辩护——比如给纯研究硬凑一份商业论证。

**例子**：我常常发现自己试图论证 [imp](https://github.com/jamii/imp) 如何适合某个这样那样的问题。这么做感觉很勉强，像是整个框架都是错的。当我明确承认——作为一个探索性项目，它本来就不打算、也不被期待去解决任何具体问题，而是去探索这样一个问题：“如果我们能用一门既更[简单](https://www.scattered-thoughts.net/writing/against-sql/#complexity-drag)、又更[有表达力](https://www.scattered-thoughts.net/writing/against-sql#inexpressive)、还更[可压缩](https://www.scattered-thoughts.net/writing/against-sql#incompressible)的语言去取代 SQL，会出现哪些新的用法？”——那一刻反倒轻松了。当我用自己真正在意的目标去衡量时，感觉自己有进展就容易得多。

### 恒定

要到任何有意思的地方都是需要时间的。有时目标必须随新信息而变，但如果目标每周都在变，那和完全没有目标也没多大区别。

在困难项目上，我尤其容易反复折腾——这类项目成功与否远未确定，我也会经历大量自我怀疑。我一直在试验给自己设定期限，比如“不管我对它感觉如何，我都会朝功能 X 推进 6 周”。这样就把那种让人麻痹的焦虑关进了专门的规划时段里，其余时间我至少在朝*某个*方向前进。

### 详尽

做出好的决策，往往取决于情境中的细微细节。

这意味着，目标需要尽可能多地包含这些细节。例如：

- 所解决问题的确切范围
- 谁会使用这些代码
- 它将在哪里运行，运行在什么样的硬件上
- 谁将维护／支持这些代码，维护多久
- 对正确输出的约束
- bug 带来的后果
- 输入数据的量、分布、变化速率
- 对吞吐量、延迟、内存占用、存储、功耗的要求

**例子**：在 [focus](https://github.com/jamii/focus) 里，我不确定该用什么数据结构来表示文本（[例如](https://marijnhaverbeke.nl/blog/codemirror-line-tree.html)、[又如](https://code.visualstudio.com/blogs/2018/03/23/text-buffer-reimplementation)）。于是我把手头所有项目里所有文件的大小都测了一遍（中位数约 2kb，最大约 2mb），也测了行长分布（约 10–1000 个字符）。我测了在我的笔记本上扫描和复制各种大小的内存块各需多久，并估算每一帧里我要做多少次这类操作。然后我用这些数字大概估算了每种数据结构的性能。结果发现，对我这个用途来说，一个简单的字符数组就足够快了。如果我当初没有弄清楚自己预期要处理哪些具体的输入，我可能就在更复杂的方案上浪费了时间（后来我确实被人“极客狙击”，去做了正是那样的复杂方案）。

**例子**：在[尝试编译查询](https://www.scattered-thoughts.net/writing/a-practical-relational-query-compiler-in-500-lines/)时，最初的目标是“简单且速度还算快”。这是个不错的起点，但不够具体，无法指引选择。这个问题中最复杂的部分是查询优化，更具体说是选择连接顺序（join ordering）。于是我把原目标操作化为：“在 [Join Order Benchmark](https://www.vldb.org/pvldb/vol9/p204-leis.pdf) 上，用不超过 1000 行代码，达到与 postgres 相当（在 ram 足够缓存全部数据的情况下）的性能”。这引导我选择了 triejoin 的一个变体，因为它可能的顺序空间足够简单，可以直接暴露给用户。它也为我选择索引数据结构提供了指引：我知道对某个给定查询，我总共只有 120 ms 的预算，并且要在几张表上做 3 次连接。所以，如果某个数据结构遍历这些表要花超过 120 ms，那它立刻出局；如果只花不到 60 ms，那它大概就够好了，我可以往下走。

有时候，细节并非全都可以拿到。比如我在做一门编程语言时，性能上其实并没有什么硬约束。但我仍然可以划下一条表明志向的界碑（比如某组基准测试或某些应用，我希望超越某个现有语言），然后用它来指引决策。

对于那些细节我一无所知的情况，我无法做出好的决策。这意味着目标不能是“面向未来、永远不过时”之类的东西，除非它同时也包含一系列同等详尽程度的可能场景。

### 渐进

如果我只有一个大而困难的目标，而它后来被发现比我以为的还要难，那我可能最后时间耗尽，不得不把一切都扔掉。

所以我喜欢设置一些各自独立有价值的子目标，覆盖从易到难的范围。完成最容易的那些目标能积攒势头，也确保我在这段时间里拿得出点东西。

**例子**：在做 [materialize 的去关联](https://www.scattered-thoughts.net/writing/materialize-decorrelation)时，我想一步到位把所有 SQL 子查询彻底去关联。一个多月过去，我还没做完，也一行代码都合不进去。而且我也没法停下来去做别的事，因为我等得越久，代码就越难合并。这变得相当有压力。如果我一开始先在 frontend 里加上对子查询的支持，但在它抵达 backend 时返回错误，那我本可以立刻合入那部分代码，然后再一个个地处理每种情况的去关联。

**例子**：对于 [dida](https://github.com/jamii/dida)，我把目标明确拆成了几步。起初我只想弄明白 differential dataflow 是怎么工作的。这一步顺利之后，我决定试着写一个更容易理解的实现，好让别人拿它当垫脚石，去理解原版。我希望最终能把它做成一个快速、可嵌入的实现，在生产中真正有用；但即便那个目标失败了，我至少还留下了对学习有用的东西。

拆分复杂目标的一个办法，是沿着技术栈做纵向切片——一个功能一个功能地推进，而不是一层一层地推进。

**例子**：在做 [materialize](https://materialize.com/) 的 sql 规划器时，我们一开始先做了一个端到端实现，只覆盖 sql 极小的一部分。然后我们一次加一个功能，每个功能从尚未实现到测试通过通常只用一两天。如果我们改成一层一层地写（先 parser，再 planner，再 optimizer 等等），那在整件事完成之前，我们就没法用上现有那些庞大的 sql 测试套件；而等到完成时，我们可能才会发现自己在某个地方彻底做错了。

### 可证伪

目标必须具体到这样一个程度：所有参与者在“它是否已经达成”这件事上都能达成一致。否则就很可能出现：每个人都在朝不同的目标努力，却以为大家在朝同一个目标努力。

**例子**：在做 [reltron](https://kevinlynagh.com/reltron/) 时，Kevin 和我以为我们已经在目标上达成了一致。但每次我们深挖某个关于交互设计的争论，就会看清：对于谁会使用它、他们会试图解决什么样的问题，我们的想法差别很大。如果我们一开始就先写详细的用户故事（Kevin 当时就是这么坚持的；），我们或许就会意识到，我们俩想造的不是同一个东西。

同理，如果一个目标不可能失败，那它就不能为“偏好某个行动方案而非另一个”提供任何理由，因此也就没有用。

**例子**：在 [Eve](http://witheve.com/deepdives/whateveis.html) 时，高层目标如此含糊，以至于我们逐月去做完全不同的问题，却察觉不到自己并没有朝任何一个特定方向前进。[《What eve is》](http://witheve.com/deepdives/whateveis.html)其实也只是把它界定为“胶水代码”和“不是系统编程”。[早期的文字](http://incidentalcomplexity.com/2014/10/16/retrospective/)全都是在讲终端用户编程（end-user programming），可[后来的 demo](http://incidentalcomplexity.com/2017/03/01/ex3-jurassicpark/) 却需要写 css。而我把大量时间花在的地方，是把性能改进到足以写出交互式 UI 的程度。面对如此含糊的问题陈述，根本不可能察觉到自己在做错事，因为我做的几乎任何东西都能说得通地套进这些目标里。

对于探索性的问题，目标通常不是解决某个问题，而是回答某个疑问。这种情况下，需要明确什么才算作一个回答。

**例子**：几年前我研究过的一个疑问是：[我能不能直接用 datalog 写简单的 webapp，从而避开对象-关系阻抗失配？](https://www.scattered-thoughts.net/writing/relational-ui/)。这个问题相当清楚地指明了如何检验成功——写几个简单的 webapp，把结果与标准工具对比。同样，如果答案是“不行”，我也希望有一份扎实的说明，讲清障碍在哪里，而不是一句“不知道，反正没成”。
