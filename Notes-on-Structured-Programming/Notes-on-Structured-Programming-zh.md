## 致读者

这些札记可以看作“写给自己的信”。我把它们写下来，是因为不这样做，我就会一遍又一遍地重复同样的论述。读过自己写的文字后，我并不总是满意。

首先，我觉得它们明显过于冗长。不过，我现在不打算压缩它们：一来，这会造成新的耽搁，而我想“继续想下去”；二来，以往的经历使我害怕被误解。许多程序员倾向于把自己遇到的困难——有时是相当特殊的困难——当作这一学科的核心，因此，对于程序设计究竟关乎什么，人们的看法大相径庭。

其次，作为一份文献，它很不完整：我十分清楚，它在尚未收束之处戛然而止。尽管如此，我还是决定把这些札记复制分发。除了一些实际考虑，主要是为了让那些对我的思考表示兴趣的人，以及那些我希望听取意见的人，了解我已经想到了什么。

我希望，尽管它有这些缺点，你仍能喜欢其中至少一部分。如果这些札记能够带来启发，或者让你重新认识程序员这门职业，我的某些目标就算达到了。

Edsger W. Dijkstra

## 一、论我们能力的局限

我面临一个基本的讲述问题。我真正关心的是大型程序的构造：其文本的规模，也许与这本小册子的全部文字相当。我又必须提供例子来说明各种技术。出于实际考虑，用于演示的程序必须很小，比我心目中“实际规模的程序”小许多倍。我的基本困难在于：恰恰是这种规模差异，构成了程序设计困难的主要来源之一！

如果我能够用小型演示程序说明各种技术，最后说：“……遇到大上一千倍的程序，也照样构造就行。”那当然很好。然而，这种常见的教学方式在这里会适得其反，因为我的一个中心论点正是：任何两件事物，只要在某一方面相差达到一百倍或更多，就完全不能相提并论。

历史已经表明，这个道理很难让人相信。显然，我们太习惯于忽略规模差异，把它们当作“并不本质的渐进差异”。我们告诉自己，能做一次，就能做两次；再借助归纳，把自己骗到相信可以按需要做任意多次。然而，事实并非如此！一千倍的差距，已经远远超出了我们的想象能力！

让我用两个例子把这一点说透。一个一岁的孩子四肢着地爬行，速度大约是每小时一英里；而每小时一千英里，则是超音速喷气飞机的速度。若把二者看作具有移动能力的物体，孩子与飞机是无法相比的：一个能做的事，另一个做不了，反之亦然。再如，你可以闭上眼睛，想象自己站在草原或海岸这样开阔的地方，远处一匹高大、没有缰绳约束的马正疾驰而来；你能够“看见”它靠近并从身旁经过。若换成一千匹这样的大马组成的方阵，你就无法在头脑中做同样的事了；倘若真能想象出来，单是恐惧就会让你的心脏漏跳好几拍！

更复杂的是，规模问题不只是妨碍我讲述，它本身就处于这一学科的核心。人们普遍低估规模所特有的困难，这似乎正是当前软件事业受挫的主要深层原因之一。对此，我只能想到一个回答：尽可能明确地处理规模问题。本节的标题由此而来。

首先，计算有其“规模”，也就是所涉及的信息量和操作次数。这一规模必须足够大；倘若真的很小，干脆不用计算机、手工完成反而更容易。自动计算机之所以有存在的理由，之所以有用，恰恰在于它能够完成我们人类无法完成的大规模计算。我们希望计算机做我们自己永远做不了的事；而当今机器的能力如此强大，即使所谓小规模计算，仅凭其规模也已远远超出我们未经辅助的想象能力。

然而，我们必须组织这些计算，使有限的能力足以保证计算产生预期效果。这种组织工作包括程序的构造，于是我们又遇到另一个规模问题：程序文本的长度。我们也应明确承认这一问题。必须记住，我们能够读写文本到什么程度，很大程度上取决于文本的规模。在我的国家，电话簿按城镇或村庄分组，每组内的用户再按姓名的字母顺序排列。我住在一个小村庄，给定一个电话号码，只需扫过几栏就能找到号码的主人；但在一座大城市里做同样的事，就成了一项大型数据处理任务！

出于同样的考虑，我想提醒读者：“清晰性”有显著的数量因素。奇怪的是，许多数学家似乎并未意识到这一点。一个定理若要在满足整整十页条件后才保证某个结论成立，就很难成为方便的工具，因为每次援引它，都必须核实全部条件。在欧氏几何中，勾股定理适用于任意三个点 A、B、C，只要能够画出一条通过 A、C 的直线，与一条通过 B、C 的直线正交。有多少数学家意识到，当 A、B、C 中某些点乃至全部点重合时，定理仍然适用？而这一点，似乎正是勾股定理用起来如此方便的重要原因。

归结起来：作为一个思维迟缓的人，我的头脑容量很小。我最好学会接受这一事实，尊重并充分承认自己的局限，而不是试图无视它们；后一种徒劳的努力，必将以失败受到惩罚。

## 二、论机制的可靠性

我以程序设计为职业，因此我谈的是程序，本节真正的主题也是程序的可靠性。不过，我在标题中用了“机制”，因为我把程序视为机制的特例；而且，我至少想明确表达一次自己的强烈感受：我关于软件的许多考虑，经过必要的调整，同样适用于硬件设计。

当今的计算机是令人惊叹的设备，但最令人惊叹的，是我们据以相信其输出有效的依据竟如此不确定。这从我们相信硬件正常工作时就已经开始了。

暂且只看硬件，想一想：我们在多大程度上能够确信它构造正确？几年前，我所在的大学安装了一台机器。文档说，它的诸多部件中包含一个定点乘法电路，可对两个 27 位整数做乘法。我们完全有理由问：“这个乘法器正确吗？它是否按照规格说明工作？”

天真的回答是：“它声称能够正确执行的不同乘法是有限的，共有 2⁵⁴ 种，那么就全部试一遍吧。”这个回答看似合理，实际上却不合理。虽然一次乘法只需几十微秒，但完成这一有限集合中的全部乘法，总时间会超过一万年！我们必须承认：即使对乘法器这样的单个部件，穷尽测试也完全不可行。（以同样的方式测试整台计算机，就意味着要确认它能够正确处理一切可能的程序！）

这一万年带来的第一个结论是：乘法器在整个寿命中，实际被要求执行的乘法，只占全部可能乘法中微不足道的一小部分，几乎等于没有！有趣的是，我们仍然要求它在接到指令时，能够正确执行任何一种乘法。这个看似惊人的质量要求，其理由在于：我们事先不知道它究竟会执行那微不足道的少数乘法中的哪些。在推理程序时，我们谈的是“乘积”，已经抽去了因子的具体值：我们不知道这些值，不想知道这些值；知道它们不是我们的职责，**不必知道它们才是我们的职责！**

我们希望用“乘积”这个概念思考，而不必顾及计算中出现的具体实例。这种愿望可以得到满足，但代价恰恰是可靠性要求：庞大集合中的**任何**一种乘法，都必须正确执行。这就是我们要求乘法器正确的理由。

那么，怎样才能令人信服地确立其正确性？只要把乘法器视为黑箱，我们唯一能做的就是“抽样测试”：提供数量可行的因子对，然后检查结果。但是，考虑到那一万年，显然我们只能测试全部可能乘法中微不足道的一小部分。某些在某种意义上“关键”的整类乘法，都可能没有接受测试。因此，相对于合理要求的可靠性，这种质量控制仍然极不令人满意。实际工作也就不采用这种办法。

由此直接得出的结论是：只要把机制当作黑箱，就无法令人信服地证明它正确；我们唯一的希望，在于不把它当作黑箱。我把这称作“把机制的结构考虑在内”。

从这里开始，我们要处理的机制就是程序。（在许多方面，程序比电路容易处理得多；电路实际上是模拟器件，还会磨损。）同样，对于程序，如果在测试时不考虑其结构，想要毫无疑问地确立正确性——哪怕只排除最轻微的怀疑——也是相当无望的。换句话说，能够在多大程度上确立程序的正确性，并不只是程序外部规格和行为的函数，而是关键地取决于其内部结构。

记住，我们真正关心的是大型程序。顺带指出，规模本身就要求我们对每个程序部件具有很高的信心。若一个部件正确的概率为 p，那么由 N 个这样的部件组成的整个程序正确的概率，大致为：

$$P = p^N.$$

N 非常大，因此，若希望 P 显著大于零，p 就必须非常、非常接近 1！

现在，如果我们认为程序员的任务不仅是编写正确的程序，还包括令人信服地证明其正确性，那么，上述论述就会深刻影响程序员的工作：他所造出的对象，必须具有**有助于推理的结构**。

本书余下部分，主要探索哪些程序结构能够发挥这种作用。下面将逐渐显现：程序正确性并非我唯一关心的事，程序的可适应性和可管理性也在其中。强调可管理性，是我的有意选择，因此我想说明其理由。

过去，普遍可用的设备能力增长，缓解了效率要求的紧迫性；但恰恰是同一增长，又带来了新的困难。有了强大的机器，人们就想使用它；所处理问题的规模，也会随设备的能力而调整。没有人会考虑编写一个需要二十年才能执行完的算法。过去十到十五年间，处理能力提高了一千倍；于是，在选择哪些问题如今应属“技术上可行”时，人类的野心大大增长。人们希望编写的程序，其规模、复杂程度和精巧程度都急剧膨胀。近几年来，已经十分清楚：整体而言，我们的程序设计能力没有跟上这些激增的要求。

可用设备的能力还会继续增长：制造商会开发更快的机器；即使没有这种发展，现在被认为特别快的机型，也会越来越普遍。我们想让机器做的事情将按比例增加。我正是根据这一推断，形成了自己对程序员任务的认识。

我的结论是：迫切需要停止主要把程序设计看作成本／性能比的最小化。我们应承认，程序设计现在就已经更是一项智力挑战：**程序设计的艺术，是组织复杂性、驾驭众多事物，并尽可能有效地避免由此滋生的混乱的艺术。**

我拒绝把效率问题视为程序员首要的关切，并不意味着我不重视效率。恰恰相反，效率考虑是修改逻辑正确的程序的主要动因之一。但我的意思是：只有在程序仍然足够容易管理的前提下，我们才有条件进行优化——无论“优化”究竟意味着什么。

本节最后，再就计算机的意义说一点旁话。计算机是极其灵活而强大的工具，许多人觉得，其应用正在改变世界的面貌。我冒昧地认为：只要我们主要把它看作工具，就可能严重低估它的意义。作为工具，它对文化的影响也许只是表面的涟漪；而作为一种智力挑战，我预期它将产生深远得多的影响！

本节前半部分的推论：

> **程序测试可以用来表明缺陷的存在，却永远不能用来表明缺陷的不存在！**

## 三、论辅助思考的工具

上一节说，程序员有义务让自己的产品具有“有助于推理的结构”；我们又把程序结构同令人信服地证明程序正确性联系起来。

然而，我们如何说服别人？如何说服自己？哪些典型思维模式使我们能够理解？本节将概览这些问题。我向专业心理学家诚挚致歉，因为这里的讨论难免外行而肤浅。不过，我希望，也相信，它足以提供一个尺度，用来衡量某种拟议结构的用处。

在帮助我们理解程序或其正确性证明的工具中，我想特别指出三种：

1. 枚举；
2. 数学归纳法；
3. 抽象。

### 3.1 枚举

在我看来，若要验证按顺序执行的一组列举出来的语句所引发的计算具有什么性质，就要诉诸枚举；其中包括区分两种或更多情形的条件子句。下面给出一个“枚举推理”的简单例子。

要求证明：对变量 `r` 和 `dd` 顺序执行以下两条语句，会保持关系式 (1) 不变。

```text
dd ≔ dd / 2;
if dd ≤ r do r ≔ r - dd
```

$$0 \le r < dd. \tag{1}$$

只需“跟着”这一小段程序走，假定开始时 (1) 成立。第一条语句把 `dd` 减半而保持 `r` 不变，执行后便有：

$$0 \le r < 2 \times dd. \tag{2}$$

现在区分两种互斥的情形。

**情形 1：`dd ≤ r`。** 结合 (2)，得到：

$$dd \le r < 2 \times dd. \tag{3}$$

此时执行 `do` 后的语句，使 `r` 减去 `dd`。由 (3) 得到最终 `0 ≤ r < dd`，即 (1) 成立。

**情形 2：`non dd ≤ r`，即 `dd > r`。** 此时跳过 `do` 后的语句，`r` 也已达到最终值。`dd > r` 与第一条语句执行后成立的 (2) 结合，立即得到 `0 ≤ r < dd`，所以在第二种情形下，(1) 同样成立。

这样，我们既完成了关系式 (1) 不变性的证明，也完成了一个包含条件子句的枚举推理实例。

### 3.2 数学归纳法

我特别提到数学归纳法，因为据我所知，它是唯一最终能让我们处理循环——例如由重复子句表达的循环——以及递归过程的推理模式。下面举一个例子。

考虑值序列：

$$d_0,d_1,d_2,d_3,\ldots \tag{1}$$

其定义为：

$$d_0=D, \tag{2a}$$

$$d_i=f(d_{i-1}),\quad i>0. \tag{2b}$$

> **译注**：所据文本在 (2b) 中写作 `i > 1`，这会使 `d₁` 没有定义；依据后续推理校订为 `i > 0`。

D 是给定值，f 是给定的可计算函数。要求使变量 `d` 等于序列中第一个满足给定可计算条件 `prop` 的值 dₖ。已知这样的值存在，且 k 有限。更正式地说，要求建立：

$$d=d_k, \tag{3}$$

其中 k 由下列条件确定：

$$\operatorname{prop}(d_k), \tag{4}$$

$$\neg\operatorname{prop}(d_i),\quad 0\le i<k. \tag{5}$$

考虑以下程序片段：

```text
d ≔ D;
while non prop(d) do d ≔ f(d)
```

上式记为程序 (6)。第一行是初始化，第二行是循环，由含义应当不言自明的重复子句 `while … do …` 控制。借用上个例子的条件子句 `if … do …`，可以更正式地说明其语义：

```text
while B do S
```

与下式语义等价：

```text
if B do
    begin S; while B do S end
```

这意味着，`non B` 是循环终止的充分必要条件。

将 `while B do S` 中的 S 称作“被重复执行的语句”。我们要证明，在程序 (6) 中，第 n 次执行这条语句后，对 n ≥ 0，有：

$$d=d_n, \tag{7a}$$

$$\neg\operatorname{prop}(d_i),\quad 0\le i<n. \tag{7b}$$

上述断言在 n = 0 时成立，这可以用枚举推理说明。接下来，也用枚举推理证明：若它对 n = N（N ≥ 0）成立，则对 n = N + 1 也成立。

第 N 次执行之后，(7a)、(7b) 对 n = N 成立。第 N + 1 次执行发生的充分必要条件是 `non prop(d)` 为真。由于 (7a) 给出 d = d_N，这意味着 `non prop(d_N)`，从而 (7b) 对 n = N + 1 成立。另一方面，d = d_N 与 (2b) 给出 f(d) = d_{N+1}。因此，第 N + 1 次执行 `d ≔ f(d)` 的净效果是建立 d = d_{N+1}，也就是 (7a) 对 n = N + 1 成立。归纳步骤至此得证。

现在证明，循环在第 k 次执行后终止。不可能发生 n > k 的第 n 次执行，因为按 (7b)，这会意味着 `non prop(dₖ)`，与 (4) 冲突。若循环在第 n 次执行后终止，则终止的充分必要条件 `non (non prop(d))`，结合 (7a)，成为：

$$\operatorname{prop}(d_n). \tag{8}$$

这又排除了 n < k 时终止的可能，否则会违反 (5)。因此，循环恰在 n = k 时终止；(3) 由 (7a) 得到，(4) 由 (8) 得到，(5) 由 (7b) 得到。证明结束。

在结束这个说明数学归纳法如何用于推理的例子之前，我还想说几句话。我不安地感觉到，有些读者——尤其是经验丰富、能力出众的程序员——此刻一定很恼火。他们认为程序 (6) 的正确性显而易见，因此不明白为何要如此大费周章：“谁都知道，满足条件的第一个序列值是什么意思，为什么要像 (3)、(4)、(5) 那样郑重其事地重述问题？难道他真指望我们这些有工作要做的人，每写这么简单的一个循环，就附上如此冗长、满是数学装饰的证明？”诸如此类。

说实话，上面证明的繁琐和冗长，也令我恼火！但目前，如果认真证明这一程序的正确性，我还做不到好多少。有时，这使我想起多年前对平面几何最初几个简单定理所作的那些令人抓狂的证明：被证明的事情，与欧几里得公理本身一样“显而易见”。

当然，我不敢建议——至少现在不敢——程序员每写一个简单循环，都有义务提供这种证明。倘若如此，他就根本写不出有任何规模的程序！这与把每个平面几何证明都明确、完整地还原到欧几里得公理一样不切实际。参见第一章。

我要表达的有三点。

第一，程序员之所以觉得 (6) 这样的构造显然正确，是因为熟悉它。我更愿意把这种行为看作无意识地援引一个他**知道**的定理，尽管他也许从未费心将它表述出来。他一生中曾经确信它为真，尽管可能已经忘记当初如何确信，而且那种方式多半不适合付印。不过，我们可以把关于程序 (6) 的断言称为“线性搜索定理”；知道这个名称，便更容易、更自然地有意识援引它。

第二，据我所知，还没有一套像上例那样、其用处得到普遍认可的定理。但这并不奇怪：这种定理体系的缺失，直接源于其研究对象——程序——尚未定型。程序员处理的对象，远没有平面几何的对象那样确定。在此期间，凭直觉就能胜任的程序员，很可能是这样的人：只要可行，就把自己限制在非常熟悉的程序结构之内；一旦构造对自己而言不寻常的东西，就变得十分警觉、谨慎。不过，对于一种已经确立的程序设计风格，寻找适用于这类程序的定理体系，可能很有价值。

第三，上个例子所需证明的长度，是不应忽视的警告。当然，也许更好的数学家能够做出短得多、更优雅的证明。就我个人而言，我更倾向于据此认定：程序设计比人们通常以为的更困难。让我们诚实地保持谦逊，把证明的长度视为一项迫切的忠告：尽可能限于简单结构，以智力上的谦逊，像躲避瘟疫一样避开“巧妙的构造”。

### 3.3 抽象

此时，我很难十分明确地说明抽象的作用，部分原因是它贯穿整个主题。考虑一个算法，以及它可能引发的一切计算过程：从这些计算过程中抽去每次所操纵的具体值，剩下的就是算法。“变量”这个概念，代表着对其当前值的抽象。

有人曾对我说——很遗憾，我记不起是谁，无法给予应有的致谢——一个人一旦理解程序设计中使用变量的方式，就理解了程序设计的精髓。回到刚才关于循环的数学归纳法，可以确认这一说法：一方面，通过抽象引入概念，才能用这些概念表述归纳步骤；另一方面，真正使“变量”概念成为必要的，正是重复执行。（没有重复执行时，只需使用“量”：其值至多定义一次，无须像变量那样重新定义。）

给一个操作命名，然后只根据“它做什么”来使用它，完全不考虑“它怎样工作”，同样包含抽象。（同样，我们应说，程序设计手册描述的是一台抽象机器；制造商交付的具体硬件，只是这一抽象机器的机械模型，而且通常并不完美！）在程序里使用一个有名称的操作而不管它怎样工作，与使用一个定理而不管它如何证明，有很强的相似性。即使证明极其复杂，定理本身仍可能十分方便！

这里，我再次提醒我们能力的局限。枚举推理在它所能覆盖的范围内很好，但我们思维迟缓，它覆盖不了很远。只有在严格的限制条件下——十分节制地使用它——枚举推理才是合适的思考工具。我们应当把抽象视为减轻枚举推理负担的主要思维技术。

英国泰丁顿国家物理实验室的 Mike Woodger 在此提出了下面的意见。我怀着感谢将其收入：“公理或定理用未经分析的术语来表述；一个有名称的操作，则预期作用于未经分析的操作数。两者之间也有相应的类比。”

## 四、一个正确性证明的例子

考虑以下程序片段，其中整数常量 a、d 满足 `a ≥ 0` 且 `d > 0`。

```text
integer r, dd;
r ≔ a; dd ≔ d;
while dd ≤ r do dd ≔ 2 * dd;
while dd ≠ d do
    begin dd ≔ dd / 2;
        if dd ≤ r do r ≔ r - dd
    end
```

为应用线性搜索定理（参见第三章“数学归纳法”），考虑如下序列：

$$dd_0=d,\qquad dd_i=2dd_{i-1}\quad(i>0).$$

用通常的数学方法可以导出：

$$dd_n=d\times2^n. \tag{1}$$

这些方法也告诉我们：因为 d > 0，对有限的 r，总存在有限的 k，使 ddₖ > r。因此，第一个循环必定终止，终止时 `dd = d × 2ᵏ`。

将递推关系 `ddᵢ = 2 × ddᵢ₋₁` 对前一项求解，得到 `ddᵢ₋₁ = ddᵢ / 2`。线性搜索定理因而告诉我们，第二个循环也会终止。事实上，第二个循环的循环体执行次数与第一个完全相同。

第一个循环终止时，`dd = ddₖ`，因此：

$$0\le r<dd. \tag{2}$$

如第三章“枚举”中所示，第二个循环的循环体保持这一关系不变。循环终止后，根据 `while dd ≠ d do`，可以断定 `dd = d`。结合 (2)，得到：

$$0\le r<d. \tag{3}$$

此外，我们证明，初始化后始终有：

$$dd\equiv0\pmod d. \tag{4}$$

例如，这可由 (1) 导出：`dd` 的可能值为 `d × 2ⁱ`，其中 `0 ≤ i ≤ k`。

下一步，验证在对 `r` 初次赋值后，下式始终成立：

$$a\equiv r\pmod d. \tag{5}$$

1. 初始赋值之后，它成立。
2. 第一个循环的循环体 `dd ≔ 2 * dd` 保持 (5) 不变，因此整个第一个循环保持 (5) 成立。
3. 第二个循环的循环体包含两条语句。第一条 `dd ≔ dd / 2` 保持 (5) 不变；第二条也保持它不变，因为它或者不改变 `r`，或者从 `r` 中减去 `dd` 的当前值，而由 (4)，这一操作仍保持 (5) 成立。因此，整个第二个循环的循环体保持 (5) 不变，整个循环也就保持 (5) 不变。

结合 (3)、(5)，最终值满足：

$$0\le r<d,\qquad a\equiv r\pmod d.$$

即，r 是 a 除以 d 所得的最小非负余数。

### 4.1 说明一：同时求商

下面的程序还会把相应的商赋给 q：

```text
integer r, dd, q;
r ≔ a; dd ≔ d; q ≔ 0;
while dd ≤ r do dd ≔ 2 * dd;
while dd ≠ d do
    begin dd ≔ dd / 2; q ≔ 2 * q;
        if dd ≤ r do begin r ≔ r - dd; q ≔ q + 1 end
    end
```

证明可以通过考察以下关系的不变性完成：

$$a=q\times dd+r.$$

这个例子来自我的同事 N. G. de Bruijn。

### 4.2 说明二：循环不变式定理

在“数学归纳法”小节中，我们证明了线性搜索定理。上述证明又使用了另一个关于循环的定理：若进入循环前某个关系 P 成立，且一次循环体执行不会破坏其真实性，那么循环终止后 P 仍然成立。这个定理显然也只能用数学归纳法证明，但证明很简单，留作读者练习。

这是十分有用的定理，常常使我们无须显式诉诸数学归纳法。还可以把它表述得更精确：对于循环

```text
while B do S
```

须证明 S 具有这样的性质：执行 S 前 `P and B` 为真，蕴含执行后 P 为真。

### 4.3 说明三：一个练习

下面的练习由美国匹兹堡卡内基梅隆大学的 James King 提供，在此致谢。

设 A、B、x、y、z 为整数，且 A > 0、B ≥ 0。证明下列程序执行后，最终有 z = Aᴮ：

```text
x ≔ A; y ≔ B; z ≔ 1;
while y ≠ 0 do
    begin if odd(y) do begin y ≔ y - 1; z ≔ z * x end;
        y ≔ y / 2; x ≔ x * x
    end
```

证明必须表明：尽管有 `y ≔ y / 2`，所有变量仍保持整数值。方法是证明以下关系的不变性：

$$x>0\quad\text{且}\quad y\ge0\quad\text{且}\quad A^B=z\times x^y.$$

> **译注**：所据文本写作 `y > 0`，并将 `x^y` 的指数写为大写 `Y`。这里将条件校订为 `y ≥ 0`，指数统一为变量 y；因为初始允许 B = 0，而循环终止时也恰有 y = 0。严格的正值条件不能作为这里的全程不变式。

## 五、论证明的有效性与实现的有效性

上一节假定了“精确无误的算术”。根据我的经验，这类证明的有效性常遭到质疑：人们认为，实际工作中永远没有精确无误的算术可用——允许的整数值通常有绝对上界，实数只能以有限精度表示，等等。那么，这些证明究竟有什么效力？

答案似乎如下：如果假定一个理想、完美的世界，并据此证明程序正确，就不该惊讶于这个理想程序在“不完美”的实现上执行时出问题。这是显然的！因此，若希望在更现实的世界里证明程序正确，就应从一开始承认：程序所调用的全部操作，尤其是算术操作，未必完美；但必须以近似公理化的方式，说明它们为使程序正确执行而应满足的性质，也就是正确性证明所依赖的性质。上一节例子中，这一要求就是在区间 [0, 2a] 内进行精确的整数算术。

> **译注**：作者的区间表述在 a = 0 或 d > 2a 时未覆盖初始化值 d。若要求所有出现的整数均可表示，统一的充分范围可写为 `[0, max(d, 2a)]`。正文保留作者的表述，以区分原文与校订意见。

编写对实数进行舍入运算的程序时，必须清楚自己所作的假设，例如：

```text
b > 0 蕴含 a + b ≥ a
a * b = b * a
-(a * b) = (-a) * b
0 * x = 0
0 + x = x
1 * x = x
……
```

这些关系成立，往往对程序逻辑至关重要。为了兼容性，程序员最好尽量少提要求；而好的实现应当满足尽可能多的合理要求。

这里适合坦白我的一个失误。在实现 ALGOL 60 时，我们决定：`x = y` 不仅在精确相等时返回 `true`，也在两值只差所表示的最低有效位时返回 `true`，否则算出 `true` 的可能性实在太小。我们当时想到的是收敛迭代：它可能在舍入精度范围内来回振荡。

我们出于好意，宽松地认定实数相等，但很快发现，所选操作的性质弱到几乎没有用处。归根到底，即使已经确认 `a = b and b = c` 为真，程序员仍不能断定 `a = c` 为真。这个决定很快就改了。

正是这次经历让我明白：程序员能够使用工具，完全有赖于工具所具有的某些性质；反过来，程序员必须能够说明自己需要哪些性质。通常程序员并不这样做，因为关于哪些性质可视为理所当然，尚无传统可循；因此，这会要求比一般情况下适宜程度更高的明确性。劣质浮点硬件机器的泛滥，加上“自动计算机主要是数值分析人员的工具”这一误解，对这门职业造成了很大伤害！

## 六、论理解程序

我一生中见过许多程序设计课程，本质上就像普通的驾驶课：教人如何操纵汽车，却不教人怎样用汽车到达目的地。

我的意思是，程序本身从来不是目的。程序的目的是引发计算过程，而计算的目的是产生预期效果。程序虽然是程序员制造的最终产品，但由它引发的可能计算过程——其“制造”留给机器！——才是这门职业真正的研究对象。例如，程序员声称程序正确时，实际上是在对它可能引发的计算过程作出断言。

整个活动的最后阶段，也就是从静态程序文本转到动态计算过程，基本上留给了机器，这又增加了复杂性。因此，在某种意义上，构造程序比构造数学理论更困难：程序与理论都是有结构、无时间性的对象；但数学理论本身就有意义，程序却只有通过执行才有意义。

本节余下部分只讨论为顺序机器编写的程序，并探索这样一种职责的后果：我们必须利用对程序的理解，对随之发生的计算过程作出断言。我的一个未经证明的主张是：能否方便、可靠地做到这一点，关键取决于二者关系是否简单，尤其取决于执行顺序控制的性质。笼统地说，我们希望程序文本的结构反映计算过程的结构。换个说法：“我们能做些什么，来缩短静态程序文本——分布在‘文本空间’中——与相应计算过程——在时间中展开——之间的概念距离？”

计算的目的是产生某种预期效果。它在离散时刻 t₀ 开始，在稍后的离散时刻 t₁ 完成；假定其效果可通过比较“t₀ 时的状态”与“t₁ 时的状态”来描述。不考虑任何中间状态时，我们把这一效果看作由一个原子动作产生。

若考虑若干中间状态，就意味着我们把时间中发生的事情划分开来，把它视为一个顺序计算过程，即若干子动作在时间上的依次发生。我们必须确信，这些子动作依次发生所累积的效果，确实等于整个计算所期望的净效果。

### 6.1 顺序连接、选择与重复

最简单的情形，是分解成固定数量、可以列举的子动作。流程图如下：

![图 1：顺序连接的流程结构](figures/EWD249-fig1.png)

必须用枚举推理来确立这种分解的有效性。此时，若要求一段线性的程序文本按照动作应当发生的次序，包含这些子动作的名称或描述，就可以缩短程序与计算过程之间的概念距离。此前保持 `0 ≤ r < dd` 不变的例子满足这一条件：

```text
dd ≔ dd / 2;
if dd ≤ r do r ≔ r - dd
```

计算的第一层分解，是两个动作依次发生。我们在程序文本中识别出这一结构：

```text
将 dd 减半;
将 r 化为模 dd 的余数
```

我们考虑所有满足 `0 ≤ r < dd` 的初始状态；对于由此考虑的全部计算过程，这种两子动作的划分都适用。到这里，一切都好。

不过，编写此程序时假定：“将 r 化为模 dd 的余数”不是原子动作，而“从 r 中减去 dd”是原子动作。查看前一个动作内部可能发生的事情，就必须区分：有些情况下执行减法，另一些情况下 r 保持不变。写成：

```text
if dd ≤ r do 从 r 中减去 dd
```

就表示：在这一细节层次上，求余动作可采取两种互斥形式之一，同时给出了选择的判据。若把 `if dd ≤ r do` 看作附加于减法动作的条件子句，那么把条件放在被控制语句之前就是自然的。在这个意义上，以下二选一子句对于两个分支语句而言，是“过度排序”的：

```text
if 条件 then 语句1 else 语句2
```

它们只是两种备选形式，在一个线性媒介中无法同时表达而不分先后。

C. A. R. Hoare 把二选一子句推广为 `case-of` 构造，允许从两个以上的可能项中选择。流程图如下：

![图 2：二分选择结构](figures/EWD249-fig2.png)

![图 3：多分支选择结构](figures/EWD249-fig3.png)

这些流程图都有顶部的单一入口与底部的单一出口。正如虚线框所示，忽略内部细节，它们又可解释为顺序计算过程中的一个动作。更精确地说，我们处理大量可能的计算过程，首先把它们都分解为同样的子动作序列；只有进一步查看虚线框内部，才发现同一个子动作，在整个计算过程集合中可能采取列举出的若干不同形式之一。

上面的结构足以处理首先分解为同一组可列举子动作的一类计算过程，却不足以处理子动作数量随具体计算而变化的一类计算。重复子句的用处在这里显现。`while 条件 do 语句` 与 `repeat 语句 until 条件` 的流程图如下：

![图 4：while 与 repeat-until 的重复结构](figures/EWD249-fig4.png)

它们也有顶部的单一入口和底部的单一出口，能表达：进一步观察时，虚线框中的动作由某类子动作依次发生“足够多次”构成。

至此，我们看到三种分解，可分别称为“顺序连接”“选择”“重复”。前两种用枚举推理理解，最后一种用数学归纳法理解。

仅使用选择子句和重复子句控制执行顺序的程序，可以直接翻译成另一种语言：该语言其余方面相同，只是必须用跳往带标号位置的跳转来表达顺序控制。反过来却不成立。换句话说，若只使用上述三种分解，所得流程图的拓扑结构受到限制；若允许从任何块画箭头到任何其他块，就有更大的自由。相对于这种自由，把自己限制在这些子句内，就是一种执行顺序纪律。

### 6.2 为什么遵守这种纪律

为什么我主张遵守这一纪律？其理由可以有多种表述。让我试着给出几种，希望其中至少一种能打动读者。

我们的一个最终目标，是构造结构良好的程序，使理解它所需的智力投入——以某种宽泛尺度衡量——与程序长度——同样以某种宽泛尺度衡量——成正比。尤其要防止枚举推理的需求爆炸。这迫使我们应用“分而治之”的古老原则，也是我们主张逐步分解计算过程的原因。

对于顺序连接式分解，我们可以用枚举推理理解，前提是第一层子动作数量足够少，而且对它们净效果的规定足够简洁。以后我会再谈这些要求，目前假定已满足。由于计算过程中的推进与程序文本中的推进，二者关系十分直接，因此根据程序文本对计算过程作出断言是可行的。

尤其是，进一步查看时，某一子动作若由选择或重复子句控制，这并不会增加理解第一层分解的负担，因为在那里只需考虑这一子动作的净效果。

由此可得：若子动作内部由选择子句控制，那么在第一层中，具体走哪条路径始终无关紧要，重要的只是走了正确的路径。同样，若内部由重复子句控制，循环体究竟执行多少次，本身也无关紧要，重要的只是执行了正确的次数。

选择子句本身可以用枚举推理理解，重复子句本身可以用数学归纳法理解。对这三种分解，我们都知道相应的推理模式；在我看来，这帮助很大。

### 6.3 描述计算进展的坐标

这种执行顺序纪律还有一个好处。理解程序时，我们建立关系。例如，在枚举推理的例子中，我们证明：

```text
dd ≔ dd / 2;
if dd ≤ r do r ≔ r - dd
```

保持 `0 ≤ r < dd` 不变。然而，即使能保证这段程序执行前关系成立，也不能断言它始终成立，尤其不保证在两条语句之间成立。换句话说，关系的有效性取决于计算推进到什么位置；这似乎是顺序过程的典型特征。

类似地，我们赋予变量某种含义。例如，一个变量记录某类事件发生的次数，如当前页上已经打印的行数。转到下一页后，立即把计数清零；打印一行后，立即加一。恰在清零或加一之前，“当前页已经打印的行数”这一解释并不有效。可见，赋予变量含义，同样只能相对于计算进展来做。这引出一个问题：“如何刻画计算过程的进展？”

我们要寻找一个坐标系，用它识别计算进展中的离散位置；还希望这个坐标系独立于程序所操纵的变量。如果需要这些变量的值才能描述计算进展，就陷入循环论证，因为我们恰恰希望相对于这一进展来解释变量的含义。

还有更严格的理由：一个永不结束的循环，可能在有限个不同状态间循环。之所以永远循环，就是因为在**不同**的进展位置，出现了**相同**的状态。此时，状态显然无法区分这两个不同的进展位置！

也可以这样提出问题：程序正在运行，计算尚未完成便在某个离散进展位置被停止。怎样识别中断点，例如为了重新计算到完全相同的位置？或者，若停止是某种运行时错误造成的，怎样在不做完整内存转储的情况下，识别计算推进到了哪里？

为简单起见，假定程序文本铺在一维文本空间中，并有一种机制，可标识与计算的离散进展位置对应的程序位置。称它为“文本索引”。如果进展位置位于相邻语句执行之间，文本索引就可以标识分号。它是一种广义的指令计数器，其值指向文本中的某一处。

若只采用顺序连接与选择分解，单个文本索引足以标识计算进展。加入重复子句后，仅有文本索引便不够了。不过，每次进入重复子句，系统可以引入一个“动态索引”，持续记录当前是该循环的第几次迭代；循环终止时，再删除它。

重复子句可以嵌套，因此合适的机制是栈，即后进先出的存储结构。开始时栈为空；进入重复子句时，在栈顶加入新的动态索引，初值为零或一；每当决定循环尚未终止，就将栈顶元素加一；每当决定循环终止，就移去栈顶元素。这一安排清楚反映：循环结束后，执行过多少次，乃至它曾经是一个循环这一事实，都不再相关。

一旦语言允许过程，单个文本索引又不够了。当索引指向过程体内部时，只有同时说明指的是哪一次过程调用，才能刻画计算的动态进展。这可以通过给出指向调用位置的文本索引来做到。因此，加入过程后，文本索引必须推广为一个文本索引栈：调用时增加一个元素，返回时减少一个元素。

关键在于，这些索引的值不受程序员控制；无论他愿意与否，它们都由程序文本或当前计算的动态展开所决定。它们提供独立坐标，用来描述计算进展；也提供一个“独立于变量”的参照系，以便赋予变量含义。

当然，即使允许自由跳转，仍有一个不依赖程序员的坐标系，能唯一描述顺序计算的进展：一种标准化时钟，记录自程序开始以来经过了多少个“离散进展位置”。它确实唯一，却完全不便使用，因为文本索引不再是这个坐标系的组成部分。

由此得到的教训是：如果承认有义务通过引发计算的程序文本，在智力上掌握这些计算过程，那么我们就应谦逊地限于最有系统性的执行顺序机制，保证“计算过程中的推进”尽可能直接地映射到“文本中的推进”。

## 七、论比较程序

程序员每天都会遇到：给定问题、算法和机器，程序仍远非唯一确定。设计过程中必须选择各种备选方案；有了正确程序后，也经常被要求修改它，例如认为另一个程序在计算所需设备资源方面更有吸引力。

这些情形引出了程序等价性问题：给定两个程序，它们引发的计算是否产生相同的净效果？对程序的给定方式、执行计算的机器、计算的“净效果”作适当形式化后，这大概能够成为一个定义明确的问题，吸引某些数学研究者。但我不打算以这种一般形式处理它。

相反，我所关心的不是任意给定的两个程序，例如两个作者独立构思出来的程序，而是可以视为同一人思考产物的备选程序。此时，问题成为：怎样构思并组织这两个程序，以便于比较它们？

我做过许多实验，从中获得的基本经验如下：两个程序若引发产生相同净效果的计算，它们就**在这一意义上**等价；但不能先验地认定它们在其他意义上也等价。若想通过比较程序来比较相应计算过程，那么，倘若在所比较的层次上，两程序中的执行顺序不同，比较就不可能，或者没有成果、不值得做、极其困难——随你怎样说。

更明确地说，只有在以下情况下，比较两个程序及其可能引发的计算才值得做：成对的计算过程可以各自划分为一个按时间依次发生的动作序列，两序列的动作可以相互对应；相应程序文本也可以同样划分为指令，每条指令对应一个这样的动作。

这是很强的条件。先看第一个例子。

### 7.1 选择与重复的层次不能随意互换

排除布尔检查的副作用，并假定 B2 的值恒定，不受 S1、S2 执行的影响，我们可以证明以下两个程序等价：

程序 (1)：

```text
if B2 then
    begin while B1 do S1 end
else
    begin while B1 do S2 end
```

程序 (2)：

```text
while B1 do
    begin if B2 then S1 else S2 end
```

第一个构造的第一层由选择子句控制，第二个由重复子句控制。我能够确立计算输出的等价性，却不能在任何其他有用意义上把它们视为等价。我不得不迫使自己接受：(1)、(2) “难以比较”。起初这一结论令我很不快，如今却已把这种不可比性视为生活中的事实；也正因此，认为在二者之间选择是一项重要设计决策，不应未经仔细考虑就作出。

恰恰是它表面上的微不足道，使我留意到哪些考虑应影响这一选择。它们超出了本节范围，希望以后再谈。

### 7.2 数组相等性的两个程序

第二个不可比性的例子稍微更微妙。

给定数组 `X[1:N]`、`Y[1:N]` 和布尔变量 `equal`，编写程序，将“两个数组逐元素相等”这一命题的真值赋给 `equal`。空数组，即 N = 0，视为相等。

引入变量 j，并赋予 `equal` 含义：“在前 j 对元素中没有发现差异。”可以写出两个程序。

程序 (3)：

```text
j ≔ 0; equal ≔ true;
while j ≠ N do
    begin j ≔ j + 1; equal ≔ equal and (X[j] = Y[j]) end
```

程序 (4)：

```text
j ≔ 0; equal ≔ true;
while j ≠ N and equal do
    begin j ≔ j + 1; equal ≔ (X[j] = Y[j]) end
```

(4) 与 (3) 的区别是，一旦发现某对元素不同，就结束重复。相同输入下，两个程序的重复次数可能不同。因此，只有把最后两行看作描述一个不可再分的动作，它们才在我们的意义上可比。但若确实要考虑它们都以循环结尾，那么它们有什么关系？为了解答，我们来证明正确性。

对数组 X、Y，定义 N + 1 个函数 EQUALⱼ（0 ≤ j ≤ N）：

$$\operatorname{EQUAL}_0=\mathrm{true},$$

$$\operatorname{EQUAL}_j=\operatorname{EQUAL}_{j-1}\ \mathrm{and}\ (X[j]=Y[j]),\quad j>0. \tag{5}$$

用这些函数表述，要求产生的净效果为 `equal = EQUAL_N`。两个程序都从 j = 0 开始，对递增的 j 保持：

$$equal=\operatorname{EQUAL}_j. \tag{6}$$

很容易想把 (3)、(4) 看作同一个抽象程序 (7) 的不同细化：

```text
j ≔ 0; equal ≔ EQUAL₀;
while “或许仍有：equal ≠ EQUAL_N” do
    begin j ≔ j + 1; “equal ≔ EQUAL_j” end
```

其中，“或许仍有：equal ≠ EQUAL_N”代表一种尚未确定的基本操作。求其值时，`equal = EQUAL_j` 成立。(3)、(4) 的区别，在于用不同判据保证 `equal` 已取得最终值 EQUAL_N。

(3) 的判据很朴素：j = N。循环体开始时仍有 `equal = EQUAL_j`；执行 `j ≔ j + 1` 后，就有 `equal = EQUAL_{j-1}`。于是：

```text
equal ≔ equal and (X[j] = Y[j])
```

只是递推式 (5) 的直接转写。

要得到 (4)，则需分析递推式 (5)。再次用数学归纳法可以导出：EQUALⱼ = false 蕴含 EQUAL_N = false，因此也蕴含 EQUALⱼ = EQUAL_N。发生这种情形时，同样能保证 `equal = EQUAL_N`，于是得到 (4)。

(4) 的循环体所需处理的子计算过程，限于初始状态 `equal = true` 的那些，因此赋值 `equal ≔ EQUAL_j` 可简化为：

```text
equal ≔ (X[j] = Y[j])
```

现在，为什么把 (7) 引入作为 (3)、(4) 的抽象会误导，已经清楚了。“或许仍有：equal ≠ EQUAL_N”说明了一个布尔表达式的真、假意味着什么，却没有说明表达式本身；这非常微妙。我们试图把 (7) 解释为一个程序：它自身层次上的部分执行顺序尚未定义，而且随细化而变。于是，又试图把 (7) 最后几行视为 (3)、(4) 最后几行共同的模型。但这会误导，因为它们引发的计算无法建立一一对应。

关于我们所说的不可比程序，就讲到这里。后面会遇到可比程序的例子。最后再说明：我们要求“成对的计算过程可以划分为按时间依次发生、并可相互对应的动作”，却没有要求成对动作的净效果相同！我们既可以比较执行同一任务的备选程序，也可以比较执行相似任务的不同程序。

## 八、逐步构造程序的第一个例子

在“论理解程序”中，我强调了有系统地安排执行顺序的必要性，使计算过程的结构能反映在程序结构中；如此，我们可以谈程序与计算过程的共同结构化。本节试图给“计算过程的结构化”这一仍相当模糊的概念增加一点具体内容。这是首次尝试利用抽象能力减少对枚举推理的需求，也是对第六章所述分解方式的一贯运用。

我不打算把所谓结构良好的程序作为成品展示，而要十分详细地描述它的构造过程。因为程序不是现成的，必须把它造出来；我特别感兴趣的，是那些我认为比较适合我们构造和理解能力的程序。

任务是：指示计算机打印前一千个素数的表，2 视为第一个素数。

**说明一。** 选择此例，是因为它一方面足够困难，可以作为程序设计中某些问题的模型；另一方面，数学背景又简单、熟悉，不会让问题本身夺去我们的注意力。

**说明二。** 我并不声称最终程序按读者所选的任何尺度衡量都会是“最好的”。在本节早期版本中，我用除法求余；至少两名读者对此反应十分激烈：“人人都知道，生成素数最有效的方法是埃拉托色尼筛法！”结果，他们再也读不下去了！

我的方法的基本模式，是以很小的步骤构造程序，每次尽量少作决定。问题分析推进，程序也随之进一步细化。

### 8.1 从整体动作到两个子动作

构造算法时，必须用对应于一套已经充分理解的指令的动作，组成所需计算。最简单的程序形式为：

**描述 0：**

```text
begin “打印前一千个素数” end
```

如果引号中的动作对应于指令集里已经充分理解的一条指令，那么描述 0 就解决了问题。为展开讨论，假定它**不**在该指令集中。于是，我们必须用“更基本”的动作构思一个计算过程，使之产生所需净效果。第一个建议，是把素数生成与打印分开。

**描述 1：**

```text
begin variable “表 p”;
    “用前一千个素数填满表 p”;
    “打印表 p”
end
```

这说明，计算由两个依次发生的动作组成，其状态空间含有一个名为“表 p”的变量。第一个动作给变量赋值，第二个由该变量当时的值控制。

如果这两个动作都在已充分理解的指令集中，而且“表 p”也是隐含可用的资源，那么问题再次解决。仍为讨论起见，假定情况并非如此。下一次细化就必须说明如何用两个进一步的子计算产生这两个动作的效果；还必须决定，尚未明确的“表 p”中间值所包含的信息如何表示。

继续之前，我想强调：写下描述 1 时，我们作出的决定何其少，原问题陈述中已考虑的内容又何其少！我们假定，以某种形式提供资源“表 p”，就能在打印开始前算出前一千个素数。在这一假定下，我们利用了素数计算可以独立于打印来构思这一事实。

从原问题中，我们所考虑的几乎只有：至少存在一千个不同素数——问题本身要有意义，就必须假定这一点。在此阶段，“素数”概念究竟意味着什么，仍基本无关紧要；我们也完全没有承诺输出的具体版式。方法的力量显然在于：原问题中这两个相当独立的方面，其后果似乎分别归入两个组成动作的细化中。这表明，我们多少成功地运用了“分而治之”的黄金原则。

但现在必须问：两个子计算能够在多大程度上独立构思？更精确地问：“是否已到可以让两名程序员彼此独立地设计两个子算法的阶段？”

当两个动作不能再被视为由已理解指令调用时，“表 p”也不能再被视为隐含可用的资源。正如要把动作分解为子计算，也要选择如何组成变量“表 p”：选择什么数据结构，表示从第一个动作经“表 p”传给第二个动作的信息？这迟早要决定；问题在于“何时”和“如何”。

原则上，似乎有两条路。

第一，尽量推迟决定如何把“表 p”组织成更中性、较少受具体问题约束的部件。接着细化一个或两个动作，假定这个仍神秘的对象具有一套适当操作。最后收集这些操作，根据它们的要求，为“表 p”设计最有吸引力的结构。

第二，现在就决定“表 p”的结构。一旦前一千个素数的表示方式确定，两个动作就可以相当独立地细化。

两条路同样棘手。例如，第一个子计算适合采用什么算法，很大程度上取决于所假定的表操作能否简洁、优雅地实现；若一项或多项操作笨拙到不可接受，整个设计就会崩塌。反过来，过早决定表结构，也可能使子计算变得别扭。绕不开这一点：在优雅的程序中，表结构与引用它的计算必须匹配良好。

我认为，高效程序员的行为可以描述为：先作最容易的决定，也就是只需最少调查——试错、反复相互调整等等——便最有理由相信将来不会后悔的决定。

### 8.2 决定数据表示与接口

为免讨论过长，假定程序员有勇气认定：现在应先决定“表 p”的结构。这样一来，立即有两种选择。

一方面，可以利用“前一千个素数的表”不只是任意一千个数字的表——不像工厂一千名员工的月薪表——而且数字互不相同。于是可用一个线性布尔数组，连续元素对应连续自然数，表示相应自然数是不是素数。数论能估计第一千个素数的数量级，从而给出足够的数组长度上界。这种组织提供了方便的机制，回答“n（小于所设上限）是不是素数？”

另一方面，可以选择一个整数数组，依次列出素数。若必须预先规定数组元素的最大值，也用同一数论估计。这种表示适于回答“k ≤ 1000 时，第 k 个素数是多少？”

我们允许程序员勇敢地选第二种。对于打印，它似乎更合适，因为要求打印素数，而不是打印自然数并标注是不是素数。对于计算阶段，它似乎也合适，只要允许程序员预见到：判断一个自然数是不是素数，会与能否找到它的素因子有关。

下个细化阶段，是仔细说明信息表示的约定，并据此重新定义两个操作。

约定如下：“表 p”的信息用 `integer array p[1:1000]` 的元素值表示。素数按值递增排列；对 1 ≤ k ≤ 1000，p[k] 等于第 k 个素数。若整数最大值隐含固定，则假定数论允许我们断言：这一上限足够大。

描述这一新细化时，又有一个困难。描述 1 是单个程序，因为它细化了描述 0 中名为“打印前一千个素数”的单个动作；用通常术语说，它可以是一个过程体。下一层却要在某种意义上同时细化三个有名称的实体：“表 p”及两个动作。因此需要标识术语，说明什么细化了什么。

暂作如下建议：描述 0 是用一个有名称动作表达的有效文本，把该动作标为 **0a**。描述 1 叫“1”，因为它是描述 0 的下一次细化；它包含对 0a 的细化，并用三个实体表达：

| 编号 | 实体 |
| --- | --- |
| 1a | 表 p |
| 1b | 用前一千个素数填满表 p |
| 1c | 打印表 p |

编号从 1 开始，因为描述 1 用它们表达；a、b、c 用来区分实体。

所选表示约定涉及 1a、1b、1c 三者，因此称为**描述 2**，用等号作分隔：

```text
1a = integer array p[1:1000]
1b = “对 k = 1 至 1000，使 p[k] 等于第 k 个素数”
1c = “对 k = 1 至 1000，打印 p[k]”
```

描述 2 的三个实体依次标为 2a、2b、2c。仅就编号看，描述 2 很单薄：只是声明，对 1a、1b、1c 分别选择细化 2a、2b、2c。

**说明。** 在选择“表 p”的信息表示时，我们没有利用各值只出现一次、且按递增顺序出现这两点。反过来，这意味着 2c 被看作打印任意一千个整数的一种具体实例；也可以是一千名编号员工的月薪表！本例打印动作的净效果，与前一千个素数一样唯一确定；但我们把它看作更广一类事件的具体实例。

继续细化 2c 时，处理的是整个类别，而数组 p 的元素值规定了其中的具体实例。人们谈论“定义接口”时，我常觉得他们忽略了这种预先作出的推广，忽略了对“可能”动作类别的构思。

若 2b、2c 已在充分理解的指令集中，2a 也隐含可用，整个问题就解决了。再次假定不是如此，就必须构思 2b、2c 的子计算。但引入第二层后，两者的细化现在可以独立设计。

### 8.3 按递增下标生成素数

现在细化 2b：“对 k = 1 至 1000，使 p[k] 等于第 k 个素数”。我们寻找描述 2b1，即 2b 的第一次细化。在 2b 后另起编号，而不叫“3 某某”，是为了表明它与 2c 的细化相互独立。

2b1 必须给出算法，说明数组元素如何取得值。例如，必须规定赋值次序。第一次细化只描述这一点，最好不多决定什么。一种显然却荒谬的版本如下，括号内为版本号：

**2b1(1)：**

```text
begin p[1] ≔ 2; p[2] ≔ 3; p[3] ≔ 5; p[4] ≔ 7; p[5] ≔ 11; … end
```

这意味着程序员已知道前一千个素数的表。我们不采用它，因为这几乎意味着不需要机器。

既然第一个素数 2 已给定，而第一千个假定程序员不知道，最自然的填表顺序似乎是下标递增。仅表达这一点，例如可得：

**2b1(2)：**

```text
begin integer k, j; k ≔ 0; j ≔ 1;
    while k < 1000 do
        begin “增大 j，直到下一个素数”;
            k ≔ k + 1; p[k] ≔ j
        end
end
```

将 k 解释为已找到的素数个数，并确认第一个素数 2 确是大于 j 初值 1 的最小素数，便容易用数学归纳法证明其正确性，假定存在足够多的素数。

若“增大 j，直到下一个素数”——称为 2b1(2)a——已在指令集中，这就是完整程序。假定不是，就必须在下一次细化中说明 j 如何增大，最好仍不多决定什么。

**层次 2b2(2)：**

```text
2b1(2)a =
    begin boolean jprime;
        repeat j ≔ j + 1;
            “使 jprime 表示：j 是素数”
        until jprime
    end
```

这里使用 `repeat-until`，表示 j 至少必须增大一次。

其正确性几乎无可怀疑。不过，如果程序员知道除 2 外所有素数都是奇数，他大概会因效率而不满意。缺乏这种“预见”的代价，是修改 2b1(2)：单独处理 2，此后循环只处理奇素数。

**2b1(3)：**

```text
begin integer k, j; p[1] ≔ 2; k ≔ 1; j ≔ 1;
    while k < 1000 do
        begin “增大奇数 j，直到下一个奇素数”;
            k ≔ k + 1; p[k] ≔ j
        end
end
```

把引号中的操作称为 2b1(3)a，类似细化得到：

**层次 2b2(3)：**

```text
2b1(3)a =
    begin boolean jprime;
        repeat j ≔ j + 2;
            “对奇数 j，使 jprime 表示：j 是素数”
        until jprime
    end
```

在两个描述层次间往返，实际上是为方便起见调整整体结构与其中基本操作之间的接口。这种往返、这种试错，确实不令人愉快；但我们缺乏充分预见，又必须依次作决定，我看不到别的办法。可以把这些努力看作成本较低的实验，探索接口放在哪里可能最方便。

**说明。** 可以宽泛地把 2b1(2)、2b1(3) 都描述为：

```text
begin “将表 p 和 j 设为初值”;
    while “表 p 未满” do
        begin “增大 j，直到下一个待加入的素数”;
            “将 j 加入表 p”
        end
end
```

但我们不这样做，因为两版本的执行顺序不同，按第七章的标准属于“不可比”。选定 2b1(3)，就意味着先前试验 2b1(2) 和 2b1(1) 不再适用，予以舍弃。

从 (2) 改为 (3)，理由是更细层次的效率收益。在 2b2 层，每次可以将 j 加二；在尚未确定的素数判定操作中，也只需分析奇数 j。

### 8.4 用已知素数试除

再次强调：2b2(3) 的算法，若素数判定操作——称为 2b2(3)a——在已理解指令集中，就已解决问题。现在假定不是，因此必须引发一项计算，判定给定奇数 j 是否有非平凡因子。直到这一步，代数才真正进入讨论。

这里利用：只需试素因子，而且所需素数已经在数组 p 填好的部分中。

具体事实如下：

1. j 是奇数，最小可能因子从 p[2] 开始，即大于 2 的最小素数。
2. 若 p[ord] 是平方大于 j 的最小素数，则最大需试的素数是 p[ord − 1]。

这里还使用了一个事实：平方大于 j 的最小素数，已经存在于表 p 中。我谦逊地引用 Don Knuth 对早期版本的意见；当时我把这一事实视为当然：

> “这里你犯了一个严重的遗漏！程序使用了一个深刻的数论结果：若 pₙ 表示第 n 个素数，我们**总有** pₙ₊₁ < pₙ²。”

我承认有错。

若这个待试集合非空，就有可能找到因子。一旦找到，便可停止调查当前 j。还需决定试验顺序：我们采用递增顺序，因为素数越小，成为 j 的因子的可能性越大。

已知 ord 时，可在 2b3(3) 层给出：

```text
2b2(3)a =
    begin integer n; n ≔ 2; jprime ≔ true;
        while n < ord and jprime do
            begin “使 jprime 表示：p[n] 不是 j 的因子”;
                n ≔ n + 1
            end
    end
```

不过，这是假定 ord 的值已知，而它是 j 的函数。也可以在这次细化开头写：

```text
begin integer n, ord;
    ord ≔ 1; while p[ord] ↑ 2 ≤ j do ord ≔ ord + 1;
    …
```

即每次需要时重新计算 ord。这里似乎应该用存储空间换计算时间：引入额外变量 ord 保存当前值；设置 j 时设置它，改变 j 时调整它。

遗憾的是，这迫使我们重写部分程序。一种办法是与 j 一起引入整数 ord，再扫描程序，凡操作 j 的地方就插入适当的 ord 操作。我不喜欢这种做法，因为在引入 j 并赋予其含义的层次，函数 ord 尚不相关。所以，我们只在恰当层次引入 ord，并且非常谨慎。

### 8.5 在适当层次引入 ord

对 2b，仿照 2b1(3)，写出：

**层次 2b1(4)：**

```text
begin integer k, j; p[1] ≔ 2; k ≔ 1;
    “将 j 设为一”;
    while k < 1000 do
        begin “增大奇数 j，直到下一个奇素数”;
            k ≔ k + 1; p[k] ≔ j
        end
end
```

所用操作为：

| 编号 | 含义 |
| --- | --- |
| 2b1(4)a | 增大奇数 j，直到下一个奇素数 |
| 2b1(4)b | 将 j 设为一 |

下一层只细化 a，b 原样向下传递。

**层次 2b2(4)：**

```text
2b1(4)a =
    begin boolean jprime;
        repeat “将 j 加二”;
            “对奇数 j，使 jprime 表示：j 是素数”
        until jprime
    end;
2b1(4)b = 2b2(4)b
```

所用操作为：

| 编号 | 含义 |
| --- | --- |
| 2b2(4)b | 仍为“将 j 设为一” |
| 2b2(4)c | 将 j 加二 |
| 2b2(4)d | 对奇数 j，使 jprime 表示：j 是素数 |

直到下一层，才需要谈 ord。因此写：

**层次 2b3(4)：**

```text
integer ord;
2b2(4)b =
    begin j ≔ 1; “初始化 ord” end;
2b2(4)c =
    begin j ≔ j + 2; “调整 ord” end;
2b2(4)d =
    begin integer n; n ≔ 2; jprime ≔ true;
        while n < ord and jprime do
            begin “使 jprime 表示：p[n] 不是 j 的因子”;
                n ≔ n + 1
            end
    end
```

所用操作为：

| 编号 | 含义 |
| --- | --- |
| 2b3(4)a | 初始化 ord |
| 2b3(4)b | 调整 ord |
| 2b3(4)c | 使 jprime 表示：p[n] 不是 j 的因子 |

下一层给出两个独立细化。可以放在连续两层中，但那就得任意规定二者次序；也可以像 2b 与 2c 那样完全分开处理，但我们觉得作这么彻底的决定还略早。

我们要表达：第一，ord 是 j 的非减函数，而 j 只增不减，所以调整 ord 就是有条件地增加它；第二，p[n] 是否为 j 的因子，取决于余数是否为零。

**层次 2b4(4)：**

```text
2b3(4)a = 2b4(4)a;
2b3(4)b =
    begin while “ord 太小” do “将 ord 加一” end;
2b3(4)c =
    begin integer r;
        “使 r 等于 j 除以 p[n] 的余数”;
        jprime ≔ (r ≠ 0)
    end
```

所用操作为：

| 编号 | 含义 |
| --- | --- |
| 2b4(4)a | 仍为“初始化 ord” |
| 2b4(4)b | ord 太小 |
| 2b4(4)c | 将 ord 加一 |
| 2b4(4)d | 使 r 等于 j 除以 p[n] 的余数 |

### 8.6 用倍数表减少计算

若有内置除法，实现求余可认为很容易。2b4(4)d 能独立细化的情形，留给有兴趣的读者。为给算法一个意外转向，我们假定没有方便的求余操作。此时：

```text
r ≔ j; while r > 0 do r ≔ r - p[n]
```

会得到非正余数，但计算时间很不理想。这再次要求引入额外的表，与引入 ord 类似。

我们想知道，对 n < ord，j 是否为 p[n] 的倍数。为此引入第二个数组，存放各个素数的倍数，并使这些倍数尽可能方便地接近 j。要给出数组大小，需要 ord 的上界。1000 当然安全，但数论给出 30 也是安全上界。因此引入：

```text
integer array mult[1:30]
```

约定：对 n < ord，mult[n] 是 p[n] 的倍数，并满足：

$$mult[n]<j+p[n].$$

这一关系在 j 增大时保持成立。要检查 p[n] 是否为 j 的因子，就在 `mult[n] < j` 时不断给 mult[n] 加上 p[n]。完成后，`mult[n] = j` 就是 j 为 p[n] 倍数的充分必要条件。

ord 的较小上界还有一个后果。“ord 太小”可表达为 `p[ord] ↑ 2 ≤ j`；但对同一个 ord，这项检查会重复许多次。可以假定，引入变量 square，使其值等于 `p[ord] ↑ 2`，能提高速度。

因此得到最后一层：

**层次 2b5(4)：**

```text
integer square; integer array mult[1:30];
2b4(4)a =
    begin ord ≔ 1; square ≔ 4 end;
2b4(4)b =
    (square ≤ j);
2b4(4)c =
    begin mult[ord] ≔ square;
        ord ≔ ord + 1; square ≔ p[ord] ↑ 2
    end;
2b4(4)d =
    begin while mult[n] < j do mult[n] ≔ mult[n] + p[n];
        r ≔ j - mult[n]
    end
```

这使我们的计算已经接近埃拉托色尼筛法的一种实现！

**说明。** 在 2b4(4)d 的细化中，将 mult[n] 与当前 j 比较时，尽量把 mult[n] 增大到需要的位置。增量也可采用 `2 * p[n]`，因为只提交奇数 j，只关心 p[n] 的奇数倍。mult[1] 一旦设置，就保持等于 4。

2c——“对 k = 1 至 1000，打印 p[k]”——的细化留给读者。我建议分五页打印，每页四列，每列包含五十个连续素数。

### 8.7 对构造过程的回顾

至此，我完成了本节开头所说的任务：十分详细地描述这样一个结构良好的程序的构造过程。最后作些评论。

最显眼的观察是：一个非常简单的程序，讨论却如此之长，确实超过了我的喜好和愿望，即使考虑到实际上做了两件事——构造程序，并广泛讨论促成它的考虑。我并不太介意后一部分长，毕竟作家会用整部小说描写人的行为；我介意的是各描述层次的文本长度。因此可以预期，记法技术将成为我们主要关心的问题之一。

但也有令人鼓舞的经验。充分承认可怜的程序员不能一次决定所有事情之后，我们在很大程度上成功地一次作一个决定，逐步建立程序。在这个例子中，不少程序已经以最终形式写定，而重大决策仍未作出。不管最终决策采用哪个方案，较早层次的代码都仍然有效。考虑到程序可管理性的要求，这十分令人鼓舞。

## 九、论程序族

上一节设计了一个完成给定任务的程序，但我们把最终程序视为孤立对象：自成一体的结构，仅按它自身的优点来评判。其结构是逐次分解的结果，目的是使正确性能够在不过度消耗智力的情况下得到证明。

本节解释为什么我更愿意把程序看作一族“相关程序”的成员，而不只是孤立对象。按传统术语，相关程序可以是同一任务的不同备选程序，也可以是完成相似任务的相似程序。

为什么程序员不能只关注必须编写的那个程序，还要考虑整个程序族？首先，除非能够把自己的行动说明为在一组同样可能采取的行动中有意作出的选择，否则很难声称知道自己在做什么。其次，若充分承认构造大型复杂程序所特有的困难，就还有一个很实际的理由。我们**必须**承认这些困难：经验表明，一个人已证明能出色完成某一规模的工作，绝不能保证面对大得多的工作时不会搞得一团糟。

大型程序的一个特点，当然是必须在其生命期中修改。常见理由是：程序虽逻辑正确，引发的计算却不令人满意，例如某些数量方面不满意。第二个理由是：程序逻辑正确，甚至很好地满足了原要求，却是对一个不完全正确的问题的完美解答；于是必须重新表述问题并调整程序。

天真的应对方式是：我们必须能够修改已有程序。为此，“程序维护”这个奇特术语已经确立。任务于是被视为文本操作。顺便说，为支持这种操作，人们还曾据此主张程序输入应使用穿孔卡片而非纸带。

然而，实际修改程序文本只是文书工作，可以用许多方式处理。我的意思是：如果主要把程序文本当作线性符号序列来掌握，那么随着文本越来越长，确定和描述究竟应修改什么，会困难到无法承受。

如果一个程序必须有两个版本，我宁愿不把一个程序的文本看作另一个程序文本的修改。如果能够在某种意义上把二者视为共同祖先的不同后代，会更有吸引力。这个祖先代表一个较抽象的程序，体现两版本的共同之处；希望它能在设计文档中容易辨认出来。意图是：

1. 两版本尽可能共享正确性证明。
2. 两版本尽可能通过机械方式共享共同或相同的代码。
3. 受修改影响的区域事先已很好地隔离；如果转换需要靠人脑在全文各处作零散修改，就不满足这一条件。

这是一个宏大的目标。其灵感来自修改程序与构造程序之间的潜在相似性：程序构造到某个中间细化阶段，已写出的内容实际上就是所有后续可能程序的合适“共同祖先”。“要改变的决定”与“尚未作出的决定”相似：两种情况下，我们保留的都是抽去这一决定后剩下的东西。

第二个灵感来源是已有经验。在从外向内、逐步细化的构造过程中，我们不仅推迟决定某些事情**如何**完成，也推迟承诺究竟**要完成什么**；随着细化推进，实际问题陈述的更多细节才进入讨论。后面的例子会比素数表更清楚地说明这一点。因此，最初几个细化层次，同样适用于一整类问题陈述。

换句话说，逐步方法建议：即使任务已明确定义，也在起初忽略给定问题的某些方面。这意味着程序员不把任务视为孤立事项，而是被引导将其视为整个任务族的一员，对问题作适当推广。通过逐次加入更多细节，最终才把算法限定为给定问题的解法。

这一切众所周知，每位称职程序员都一直这样做。我仍要强调，原因有几种。如果问题陈述复杂到不能一眼把握，就**必须**这样接近并剖析它，参见第一章。其次，即使问题已完全定义，也应谨慎地预想尽可能多的未来变化，并为可容纳的变化作准备。

这并不是邀请人把程序做得“通用”到效率不可接受。若问题推广欠考虑，很容易如此；若推广由销售部门指定，就更容易如此！但根据我的经验，即使在传统程序设计中，寻找可行且可能有用的推广，也很值得，因为这种考虑能明确指引最终程序的结构。而这种考虑归根到底，就是或多或少明确地构思整个程序族！

在“论机制的可靠性”中，精心组织程序结构的必要性，是由正确性必须可证明这一要求推导出的。本节又遇到一个理由：程序结构应当预先照顾其适应与修改。程序不仅要通过结构反映我们的理解，还应从结构上清楚看出，哪些调整能够顺利处理。谢天谢地，这两个要求相辅相成。

## 十、论以存储空间换取计算速度

在当今的顺序计算机中——这里指 1969 年春——可以区分两个主要部件：主动部件处理器，以及被动部件存储器。前者的特定职责是快，后者的特定职责是大。下面假定，这种功能划分会持续足够久，值得研究它的后果。

从程序员角度看，存储空间与计算时间是两种不同资源。我认为分配它们、在二者间分担负荷，是程序员而非系统的责任之一。本节讨论这种责任的后果，不讨论估计各种负荷的技术，也不给出影响选择的定量判据，而讨论各备选方案之间的逻辑关系。

**说明。** 某些选择交给系统，并非不可想象。但除最简单的情况外，设计方案并确立等价性，似乎仍需程序员作出数学上的创造。自动化这种问题求解活动的努力，都不在本书范围内。

### 10.1 保存函数值与按需更新

最简单的情形是：计算经常需要 `FUN(arg)` 的值。FUN 是给定可计算函数，定义在一个或多个已存储变量的当前值上，这些变量统称 arg。版本 A 只存 arg，需要时计算 FUN(arg)。版本 B 引入额外变量 fun，其唯一目的，是记录与 arg 当前值对应的 FUN(arg)。

版本 A 中出现：

```text
arg ≔ …
```

即对 arg 赋值；版本 B 则出现：

```text
arg ≔ …; fun ≔ FUN(arg)
```

从而保持 `fun = FUN(arg)`。因此，凡 A 需要求 FUN(arg) 的地方，B 只需取 fun 的当前值。

偏好 B 可能有两个理由。第一，若读取 FUN(arg) 比对 arg 赋值更频繁，B 就可能少用计算时间。必要时，还可增加布尔变量“fun 已更新”，表示是否认为 `fun = FUN(arg)` 成立。对 arg 赋值时，同时：

```text
“fun 已更新” ≔ false
```

每次需要 FUN(arg)，先检查此变量，看是否必须重算；若须重算，把结果赋给 fun，并按含义将“fun 已更新”置为 true。称最后这个方案为版本 C。

三个程序仅在 A 对 arg 赋值或使用 FUN(arg) 的地方不同，显然就输出而言等价。用机械方式从 A 导出 B 或 C，也并非不可想象。

### 10.2 利用变化规律增量更新

但情形常没有这么简单。现在谈引入 fun 的第二个理由：对任意 arg 从头计算 FUN(arg)，往往很不合算；而在 arg 改变时计算 FUN(arg) 如何变化，却容易得多。此时，调整 fun 与函数依赖的性质之间的联系，比 `arg ≔ …; fun ≔ FUN(arg)` 所暗示的更紧密。

这种可能性不仅与函数依赖的性质密切相关，也常与计算推进时“变量 arg 的历史”相关。素数表程序引入 ord，就是一个鲜明的例子。ord 是依赖 j 的函数，是满足下式的最小值：

$$p[ord]^2>j.$$

正因为 j 随时间单调增加，调整 ord 才是很有吸引力的操作。

在我对程序的理解中，希望这类保存冗余信息的额外变量，能清楚地被认作额外变量；即使函数关系不是十分确定，例如同一例子中的 mult 表，也如此。我很倾向于将这样的程序看作更抽象程序的优化细化，即使额外变量实现的优化，对达到实际可接受性能必不可少。

从效率角度，这样的变量可能重要到令人觉得：设想一个抽去了它的层次，是不负责任的白日梦。操纵这些变量的方式，往往被体验为算法的主体；我们数学才智的成果也常在这里收获。

关键在于：虽然至少一种这种优化细化的可能性，对得到实际性能必不可少，但仔细观察，常会发现，即使在最粗略的层次上，它也远非唯一。

**说明。** 我记得有一个程序，额外信息冗余到不仅能从 arg 导出 fun，也能反过来导出 arg。二者关系突然变得对称，我便被一个问题严重困扰：我凭什么非对称地处理它们？

该程序生成某个组合谜题的所有解。仔细查看后发现，还存在第二个组合谜题，并能证明两个问题的解之间有一一对应。如果解决的是第二个问题，fun 与 arg 的角色就会互换！在传统程序设计中，这类函数依赖不明确显示，两谜题很可能由完全相同的程序解决；但我构造了两个结构不同的程序。

我认为这是正确的。因为用同一个程序解决两个谜题，需要的正确性证明随所解谜题而不同。若还要求程序结构反映对计算过程的理解，这种做法似乎就不太合理！

## 十一、论一种程序模型

在拥有程序之前，必须先构造它；拥有之后，若编写它有意义，就会执行它。本节不着重讨论构造和执行活动，而试着把程序视为静态对象。我们希望它是高度结构化的对象，主要问题是：设想什么结构，为什么？希望最终得到既方便构造又方便执行的程序结构。

当然，我在思考时不可能忽略这两个过程，但目前不想讨论它们；尤其不讨论设计方法——从外向内还是反过来——也不讨论实现上的后果。仍为避免过分复杂，只讨论顺序程序。

如果只评判程序本身，我的中心想法是：希望程序按我能够理解的方式写下，按我愿意向别人解释它的方式写下。不过，不再限定的话，这只是人人赞成的空泛主张。让我尝试具体一点。

### 11.1 从区域注释到抽象指令

考虑一个非常简单的计算，可分辨出三个依次发生的动作：输入数据、处理数据——即计算本身——输出结果。一种程序表示是长串语句：

```text
begin
    …
    …
    …
    …
    …
    …
end
```

再进一步，为解释加些标号：

```text
begin
    输入开始：…
              …
    处理开始：…
              …
    输出开始：…
              …
end
```

读文本时，这些标号提示接下来发生什么。更好一些，可以写：

```text
begin
    输入：begin …
                … end;
    处理：begin …
                … end;
    输出：begin …
                … end
end
```

此时，把标号与其说看作程序文本中某个点的标记，不如看作其后 `begin-end` 所界定区域的名称，或者看作计算所分解成的三个动作的名称。

但即使这样，它们仍然只是注释，是给有兴趣的人类读者的解释性附加文字；我却希望它们成为程序不可分割的一部分。希望程序文本在某处明确反映：无论进一步查看时三个动作是什么形式，计算已分解为它们依次发生。

一种办法，是在某处写下三个抽象语句的文本序列：

```text
输入; 处理; 输出
```

约定：这三个动作的时间顺序确由上述文本顺序控制，而进一步细化写在“别处”，也许分开写，但肯定不规定相对次序。

如果闭式子程序不是二十多年前就已发明，现在便是发明它的时候！也就是说，我们又回到熟悉的领域，以致许多读者会觉得上当。我却不这样想：只要经过验证的方法仍令人满意，坚持它就不该羞愧。但应清楚知道，希望从它得到哪些好处；必要时调整它，最后为使用它建立纪律。所以让我回顾子程序概念，因为过去一年，我对它的评价改变了。

### 11.2 子程序、过程与局部变量

我最初通过 EDSAC 接触闭式子程序概念，参见本章末尾的参考文献。子程序是标准程序库的基础。那时构造硬件本身是巨大冒险；许多标准例程，是以稀缺的存储空间和计算时间换取电路的手段。例如，指令集中没有除法指令，就提供除法子程序。

奇怪的是，我不记得当时曾把子程序理解为将给定机器“重建”为更合适机器的手段；也不记得主要把它看作用户为反映自己的分析而构思、构造的对象。它们更多是供用户使用的标准例程。后来，我主要把它们看作缩短程序长度的手段。

但整个程序仍被构思为在单一、均匀的存储器中活动，在没有结构的状态空间中活动；整个计算仍被构思为一个处理器执行的单一顺序过程。以后几年，我在许多程序设计课中忠实宣讲这一套，常解释调用序列如何传递返回地址，子程序又如何在开始时设置自己末尾的“链接”，即返回跳转。

现在，我更愿意认为主程序有自己的指令计数器：子程序执行完后，它继续“计数”；绝不把其“休眠中的值”视为传给子程序的参数。

然而，旧观点已经进入许多机器的硬件。有些机器的子程序跳转把链接存入子程序的“零号地址”，从“一号地址”继续取指，这使可重入代码和递归子程序较难实现。甚至在本十年里，有些机器在程序中断时，仍把被中断程序的“程序状态”存到与中断相关的位置，而非与被中断程序相关的位置！

十年后，ALGOL 60 出现，局面改变了；我们不再叫它闭式子程序，而叫“过程”。程序员仍视它为缩短程序文本的方便手段；越来越多的人也开始用它组织结构，使针对预见到的规格变化的调整，只需替换一个或几个过程体，或者改变调用的若干实参。但最主要的新东西，是局部变量概念。

它体现在两个重要方面。

第一是**作用域**：不是所有变量在整个程序中都同样可访问。过程的局部变量在过程体外不可访问，因为在外部它们无关紧要。过程为完成自己的任务需要什么局部变量，是其私事，不关调用它的主程序的事。主程序能够，而且**必须**独立于这些局部变量来构思；这一事实得到了审慎的反映。我们可以对 ALGOL 60 的具体作用域规则有所疑虑，但应承认，它是朝正确方向迈出的重要一步。

第二，过程可以递归使用；更精确地说，允许直接或间接调用自身。关于这种能力的好处，曾有许多激烈争论；据我所见，讨论已经平息。反对递归过程的理由始终是效率：不可重入代码能执行得快得多。

但多道程序设计的出现，又带来了灵活分配存储空间的需求。若仍有机器执行不可重入代码明显更快，即对递归例程施加过重代价，我冒昧地认为，它的结构如今应被称为有些过时。

递归过程迫使我们承认：静态的过程文本，与动态的激活——有人称为它的一次“化身”——不同。过程文本是一回事，这一次所操作的局部变量集合，是另一回事。

### 11.3 过程概念的局限

到这里都很好。现在说不足，无论称作语言上的还是概念上的都可以。

局部变量在进入过程时“创建”，退出时“消灭”。正是对某次过程激活所属变量生命期的这种自动控制，使我们能用栈，即后进先出的存储安排，实现递归过程。局部变量只在所属激活期间存在，这使过程无法在幕后把信息从一次激活传给下一次。

为克服这一点，引入了 `own` 概念，但它没有解决问题。一方面，递归情况下 `own` 变量到底适合做什么，很不清楚；另一方面，不能编写一组共享若干 `own` 变量的过程。可以把变量声明在包含过程声明的外层块里来模拟，但作用域规则会使它们过于广泛地可访问，不能再看作“幕后”的东西。

我们的结论——既非新观点，也绝非我一人的观点——是：ALGOL 60 的 `own` 概念考虑不周，必须寻找新的方式，控制并描述局部变量的生命期、可访问性与身份。

我对过程概念还有一个意见：它仍主要被看作缩短程序文本的手段，尽管递归时被缩短的文本长度可能未知。过程调用的语义用著名的“复制规则”描述：调用被理解为简写；从语义上，应以过程体文本的一份副本替换它，适当调整标识符并替换参数，再由执行主程序的同一机器执行修改后的文本。

于是，它仍是由单一顺序机器执行的一段程序文本，或其表示。而恰恰是这一单一机器的图景，现在已不能让我满意。

### 11.4 虚拟机器的分层层次

我希望把主程序看作由它自己的专用机器执行：该机器有合适的指令集，操作合适的变量，并在自身指令计数器控制下安排执行顺序。这样，若拥有这台机器，主程序就会解决我的问题。

之所以希望这样看，是因为它强调：不管这台机器——很可能仍是虚拟的——是否可用，都可以讨论并确立主程序的正确性。我不必拥有它，只需拥有与正确执行当前主程序相关的规格说明。

对我而言，构思虚拟机器体现了抽象能力。这与理解高级语言程序类似：无须知道乘法、下标访问等操作如何实现，也无须知道最终负责执行的硬件采用什么数制这样的无关细节。

实际中，这台理想机器当然往往不存在。于是，下个任务——在结构上类似原任务——是编程模拟“上层”机器。为此必须决定数据结构，为上层机器提供状态空间；还需构造一组算法，各自实现上层机器指令集所假定的一条指令。最后，“下层”机器可有为自身方便而引入的私有变量，完全不在上层机器的领域和作用域内。

但这一组程序所针对的机器，极可能也不存在。因此下个工作，又是用再下一层机器的程序模拟它，如此继续，直到得到硬件能够执行的程序。

若能沿此思路建立程序，就把它组织成了若干层。每一程序层都应能在假定有合适机器执行它的前提下独立理解；而每一层的功能，则是模拟紧邻上层所假定可用的机器。

为什么采用此模型？希望得到什么好处？试列如下：

1. 第八章的经验强烈表明：对应不同抽象层次的分层安排，是很有吸引力的程序构造载体。
2. 可以合理希望，许多程序修改可表述为用兼容的机器替换某台虚拟机器。
3. 希望它能帮助掌握运行中修改程序所产生的问题。如果某层机器停在两条指令之间，所有下层机器完全静止，可以替换；所有上层机器则应视为正处于某条指令的执行中，其状态仍在转换。顺序机器的状态只能在指令执行之间解释。若想随时判定哪些解释有效，那么每台机器都有自己指令计数器、各自“数自己的指令”的层次图景，更有用。通常语言以同一种尺度，例如单条语句的“粒度”，衡量计算进展；此时面对“哪些解释何时有效”的问题，我就有些无从着手。
4. 希望模型还能帮助处理检测到故障后的全部或局部恢复问题。我最近参与设计、构造一个多道程序系统；最恼人的事之一，是某个存储单元发出奇偶校验报警时，我们完全无法用机械方式估计灾难范围。唯一能实现的安全反应，是立即停止整台机器；这实在不是值得自豪的方案！
5. 分层机器的层次图景，能抑制无节制使用“分而治之”的一种危险：各部件编写得过于独立，造成重复劳动，甚至更糟。某层含有由某台概念机器执行的“一组程序”，这强调同组程序应共享相同的基本操作。分工是好事，但另一方面，还必须把分散的线头重新接起来！

本章参考文献：M. V. Wilkes、D. J. Wheeler、S. Gill，*The Preparation of Programs for an Electronic Digital Computer; with Special Reference to the EDSAC and the Use of a Library of Subroutines*（《电子数字计算机程序的编制：特别论及 EDSAC 与子程序库的使用》），Addison-Wesley Press，1951 年。

## 十二、逐步构造程序的第二个例子

程序结构作为分层机器体系的图景逐渐显现，我已经跃跃欲试，想拿它再编一个程序。这里使用的记法不应视为经过周密考虑的建议：它们只是按我的兴致选择，是实验的一部分。

### 12.1 问题：用行式打印机绘图

有一台行式打印机，由两条命令控制。`NLCR`（New Line Carriage Return，换行回车）把下一行最左端位置设为“当前可打印位置”；`PRSYM(n)` 在当前可打印位置打印由整数参数 n 指定的字符，再把其右邻位置设为新的当前可打印位置。为讨论方便，可允许行长无限。

只使用 n 的两个具体值，分别称为 `space` 和 `mark`。`PRSYM(space)` 让当前位置保持空白；`PRSYM(mark)` 打印一个给定可见字符，例如某种星号。

另给定两个以整数为自变量、取整数值的函数，满足：

$$0\le i<1000\quad\Longrightarrow\quad0\le fx(i)<100,\quad0\le fy(i)<50.$$

要求编写程序打印 50 行。从上到下，y 坐标依次为 49 到 0；每行从左到右，x 坐标为 0 到 99。对于某个满足 0 ≤ i < 1000 的 i，若某位置有：

$$x=fx(i),\qquad y=fy(i),$$

就在该位置打印标记，共一千个位置，若重合则更少；其余位置保持空白。也就是说，曲线以离散参数形式给定，我们要把行式打印机当作数字绘图仪使用。

我在口试中广泛使用这一问题。大多数学生很快发现：没有 `OLCR`（Old Line Carriage Return，返回原行行首）和“退格”，可打印位置的处理顺序由打印命令规定；这个顺序又与按 i 递增排列的标记顺序毫无关系。

于是，他们很快得出结论：似乎应使用存储器。先扫描一千个 i 值，以方便的方式存下页面图像；再在该图像控制下打印。更精确地说，假定计算机有足够存储空间，而 fx(i)、fy(i) 的计算可能很耗时，因此希望每个 i 只计算一次。

### 12.2 COMPFIRST：先构造图像，再打印

将这一设计决定记录如下：

```text
COMPFIRST
begin
    draw: {build; print};
    var image;
    instr build(image), print(image)
end
```

这段文档视为最终程序的组成部分，解释如下。

它针对名为 COMPFIRST 的机器。机器名用大写，尽量表达该机器程序所反映的决定类型。

接下来给出有名称的算法 draw，假定它是整个待构造绘图程序的名字。算法表示两个动作的所需时间顺序：先在存储器中构造图像，再按已存的值在纸上打印。

最后两行是声明或声明头部，命名运行上述算法所需机器的部件。image 是容纳页面图像的数据结构；它是该机器状态空间的唯一组成部分。指令集包含 build 和 print 两条指令。

继续前，需要指出两个缩写，我尚不知道它们是很明智还是很愚蠢。它们都源于：image 是该类型的唯一变量。

如果状态空间要包含两个图像，我会写：

```text
type image;
image var image1, image2
```

表示两个变量 image1、image2 具有相同的可能值集合；这一集合由名为 image 的**类型**刻画。以后详细说明 image 类型时，对两个变量都适用。

由于此类型变量只有一个，我冒险不区分集合及其唯一元素，二者都称 image。在 COMPFIRST 的描述中，如 `build(image)`，image 指变量；以后给结构细节时，它指类型。

最后一行的指令声明类似过程头部。通常，它们包含参数类型，而调用包含作为实参的变量。但若类型唯一决定了参数，这样区分似乎没有意义；所以我在声明里写实参，却在 draw 的算法代码中省略 image。于是，显式实参记法可留给确实使用组合选择自由的情形。

我想强调：名为 draw 的小算法，可以而且应当看作针对一台机器写的程序。应为这台机器写手册，说明：

1. build 给 image 赋值，使之表示由 fx、fy 指定、应在纸上打印的图像。
2. print 按 image 当前值所规定的图像，在纸上打印。

考虑 draw 的其他算法，或许最容易看出它确实是机器程序：

```text
draw: {print; build}
```

这是错的，因为此时 print 动作未定义。

```text
draw: {build; build; print}
```

正确，但多耗时间：第二次 build 赋给 image 的值，就是它已有的值。

```text
draw: {build; print; print}
```

则有意义，会把图像打印两次。

回到任务。如果有 COMPFIRST，draw 就完成工作。为讨论起见，也为符合实际，假定没有这样按需要定制的机器。那么，下个与前任务相似的任务，就是造出这台机器。

假定了三个实体：build、print、image，前两个都引用后者。因此，进一步规定 image 会影响前两个；不进一步承诺 image 的结构，也很难细化 print。但 build 可以独立进一步细化，所以首先选它。

### 12.3 CLEARFIRST：先清空，再设置标记

必须描述 image 如何取得正确放置一千个标记的值。从整体看，这给一个先前值未定义的变量赋值。若预想逐个添加标记，那么添加下一个标记将是作用于 image 已定义值的动作。因此，把整个设置过程看作作用于已定义的空白页值，似乎很合适。

这个决定得到：

```text
CLEARFIRST
begin
    build: {clear; setmarks};
    instr clear(image), setmarks(image)
end
```

clear 将 image 设为五十行空白图像；setmarks 调整此初值，加入曲线的一千个或更少标记。

CLEARFIRST 同样允许其他程序：

```text
build: {clear}
```

有意义，但输出五十行空白。

```text
build: {setmarks; clear}
```

含有未定义操作。

```text
build: {clear; clear; setmarks}
```

含有多余操作。下面也一样：

```text
build: {clear; setmarks; setmarks}
```

第二次 setmarks 只添加已经存在的标记，不改变 image 的值。

**记法说明。** 用 clear、setmarks 解释 build 时不显式写 image，因为除非机器确实使用实参选择上的自由，否则不想在算法中使用实参记法。此外，build 只有一个参数，没有为形参引入单独标识符。这种缩写也可能很不明智。

### 12.4 ISCANNER 与 COMPPOS：遍历标记并求坐标

下一个无需进一步承诺就能作出的决定，是描述如何依次处理曲线的一千个标记。暂用如下写法：

```text
ISCANNER
begin integer i;
    setmarks: {i ≔ 0;
        while i < 1000 do {add mark; i plus 1}};
    instr add mark(i, image)
end
```

在理解这一算法时，假定机器的指令集中有 `add mark(i, image)`，按添加第 i 个标记的要求改变 image。算法规定处理次序，表明所有标记都恰好处理一次。

但这并非全部。还引入了新变量 i，算法调用一组引用它的动作：`i ≔ 0`、`i < 1000`、`i plus 1`。如果完全一致，似乎也应把它们与 add mark 一样列在底部，表示以后可能需进一步说明。我没有这样做，而是像对待 `while-do` 一样处理它们。从语言语义角度，这种单独对待隐含已理解类型 integer 的方式似乎不理想，也难以解释为什么 integer 与 image 的待遇不同：在这台机器中，二者都隐含已理解。

然而我确实这样做了。我一直为不存在的机器设计程序，然后说：“如果现在有一台具有所假定基本操作的机器，任务就完成了。”逻辑上正确，实际中却是个玩笑，因为我们很清楚，不可能假定有一台通用机器，其指令集如此贴合需求。

不应忽视，也不应佯装忽视，在后续设计中提供这些基本操作的责任。以这种特殊方式援引已理解的 integer 类型及其操作，是为了表达：这些能力虽必须以某种形式提供，但提供它们不在程序员的责任范围内，而且程序员接受其任何合理实现。

又剩下一个无需承诺其他基本操作就可细化的操作。须说明：处理第 i 个标记，如何转为处理页面中的一个位置。构造负责计算位置的机器：

```text
COMPPOS
begin integer x, y;
    add mark: {x ≔ fx(i); y ≔ fy(i); mark pos};
    instr mark pos(x, y, image)
end
```

mark pos 按在待打印图像的 (x, y) 位置增加标记的要求，改变 image 当前值。

**说明。** 此次细化明确假定，可按自变量的任意顺序计算 fx(i)、fy(i)。若这两千个函数值要从输入流中，按规定 i 顺序成对读取，则最后两台机器必须合并。

### 12.5 为什么可以推迟表示决定

现在，我看不出不承诺尚模糊的 image 类型结构就能继续细化的可能。它的值如何存储？必须组织 image 类型的变量，也就是选择其可能值的表示方式。

我在不同地方讲过这个程序的不同版本。值得指出：至少两次，部分听众到这里时已经深感不安。例如，他们认为我不能声称已完成部分的程序正确；他们反对我说 `draw: {build; print; print}` 会打印两次相同图像，因为在**造出** print 之前，我怎么知道它不会通过副作用改变 image？

答案当然是：print 必须做规定它做的事，不应做未规定的事。但还有更多反对意见：我未证明表示唯一；也许 print 只是偏函数，在 image 的某些可能值上未定义，等等。

我的回答是：这些关切虽合理，却应在合适时机处理，也就是在承诺一种表示时，而不是此前。方法的力量，显然正在于：这么多程序能够独立于 image 值的表示方式写下。迄今所做的，确实似乎是审慎地利用了抽象能力；这里抽去的是数据结构 image 的具体表示。

即使现在认定该决定 image 数据结构了，也不必一次完全承诺。面对如何组织变量的问题，可以逐步决定，就像前面的算法细化一样。

### 12.6 LINER：把图像表示为行数组

回想问题来源：PRSYM、NLCR 迫使计算从上到下逐行输出图像。试着用行数组组成图像，来反映这一事实。下一层如下：

```text
LINER
begin integer j;
    image: {array line[0:49]};
    print: {j ≔ 49;
        while j ≥ 0 do {lineprint(line[j]); j minus 1}};
    clear: {j ≔ 49;
        while j ≥ 0 do {lineclear(line[j]); j minus 1}};
    mark pos: {linemark(line[y])};
    type line;
    instr lineprint(line), lineclear(line), linemark(x, line)
end
```

> **译注**：原文 clear 的循环体开头误用左圆括号，此处统一为与右花括号匹配的左花括号。`linemark(line[y])` 沿用作者省略唯一确定参数 x 的实验记法。

倒数第二行引入 line 类型。回顾一下：类型是一组可以区分的值；此类型变量在任一时刻，可取其中一个值。第一行定义说明：image 类型由 50 个 line 类型元素组成，编号 0 到 49。由于只有一种类型由它组成，我们仍未引入新的标识符，不论这样明智与否。

print、clear、mark pos 原来是对 image 的操作，现在译成用行操作表达的算法。代码里的真正实参，指定是哪一行；描述末尾列出指令，说明动作作用于“一行”，给出了类型，但不是具体参数。

本层引入新特点。首先，数据类型的结构细化，如 image，与算法细化，如 print、clear、mark pos，被放在很相近的地位。此前，可把方法视为为“子程序化”建立纪律——请原谅读者容忍这个可怕术语！如今可见，这只概括了一半目标，因为我们也试图对数据结构应用类似技术。

其次，以前的机器只解释一个实体，即一条指令或一种数据类型，而 LINER 解释整组实体。关键是尽量每层对应一个独立设计决定。这里的决定，是从此用行来理解图像，因此所有直接处理图像的操作都要译成处理其各行的操作。

图像已通过解释被消解，只剩 line 这一不寻常类型需要处理。下一层就做这件事。请注意：下一层只处理行；行被用来组成图像，已经无关紧要！

### 12.7 LONGREP：用字符数组表示一行

表示一行有许多可能，例如：列出应打印标记位置的 x 坐标，可按递增顺序排序；用 100 元素的布尔数组表示相应位置是否应有标记；或用 100 元素的整数数组，每元素保存对应位置 PRSYM 参数值 mark 或 space。

最后一种便于扩展：可以在同一图像中打印以不同标记表示的不同曲线，所以选它。得到：

```text
LONGREP
begin integer k;
    line: {integer array sym[0:99]};
    lineprint: {k ≔ 0;
        while k < 100 do {PRSYM(sym[k]); k plus 1};
        NLCR};
    lineclear: {k ≔ 0;
        while k < 100 do {sym[k] ≔ space; k plus 1}};
    linemark: {sym[x] ≔ mark}
end
```

但这一实现会用空格填满最右标记右边的余下行长，就像写信要转到新段落时，却不停敲空格键直到铃响！

### 12.8 SHORTREP：只打印必要部分

下一版省去多余 PRSYM 命令，甚至让 line 变量中不必定义的元素保持未定义。每行关联一个计数器 f，表示该行所需 PRSYM 命令数。清空一行现在简化为把 f 置零！

```text
SHORTREP
begin integer k;
    line: {integer f; integer array sym[0:99]};
    lineprint: {k ≔ 0;
        while k < f do {PRSYM(sym[k]); k plus 1};
        NLCR};
    lineclear: {f ≔ 0};
    linemark: {sym[x] ≔ mark;
        if f ≤ x do {
            k ≔ f;
            while k < x do {sym[k] ≔ space; k plus 1};
            f ≔ x + 1}}
end
```

### 12.9 后补说明：让正确性更容易理解

上面的程序基本就是我向至少五组听众展示过的程序。两个月后的现在，我从容思考正确性证明时，突然意识到：给出的 linemark 算法暴露了我的旧习惯；与下面的备选方案相比，它是一段糟糕的代码：

```text
linemark: {
    while f ≤ x do {sym[f] ≔ space; f plus 1};
    sym[x] ≔ mark}
```

这一版本保证：每次执行 `sym[x] ≔ mark` 时，关系 `x < f` 总是成立；第一行的功能恰是确保这一点。请读者试着理解两版本并比较所需推理，随后就会同意我对原版的评价。

这个第二版本，源于以下观察。程序中的条件语句：

```text
if B do S
```

有两种用法。一种是执行 S 不会使 B 由真变假；另一种是保证执行 S 会使 B 由真变假。后一种情况下，条件语句的功能，是确保执行后 B 不成立。

于是，它本质上是以下循环的简写：

```text
while B do S
```

循环具有使 B 不再为真的性质，只要它终止。但要证明这种简写合理，须另行证明：循环体至多执行一次。在第八章 2b4(4) 层，我们写：

```text
while “ord 太小” do “将 ord 加一”
```

当时没有费心引入这种简写；其实那里用条件子句也能完成任务！

## 十三、论我们已经取得的成果

思考所设想的程序结构时，我常使用的一个比喻，是把程序看作由一颗颗珍珠串成的项链。

我们按层描述程序，每层都包含对上层假定可用实体的细化。细化或者是动态的，即算法；或者是静态的，即数据结构；它们都应由适当的机器来理解。我用“珍珠”指这样的机器，连同其所包含的细化。

上一节程序由六颗珍珠组成的项链构成，顺序为以下两者之一：

```text
COMPFIRST         COMPFIRST
CLEARFIRST        CLEARFIRST
ISCANNER          ISCANNER
COMPPOS           COMPPOS
LINER             LINER
LONGREP           SHORTREP
```

LONGREP、SHORTREP 是不同珍珠：它们将“上表面”的相同概念，解释为“下表面”的相同概念；仅具体细化不同。它们就像针对同一任务、同一机器的不同备选程序。

改变程序，将被视为用一颗或多颗其他珍珠，替换原项链中的一颗或多颗珍珠。珍珠是构成程序的独立单位。构造程序，作为构造相关程序类中的一个成员，现在被看作两阶段过程：先制作比严格所需更多的珍珠，再从其中选出一部分，串成一条匹配的项链。

### 13.1 为什么用珍珠作为修改单位

采用两阶段方法的理由很多。设计时必须考虑许多备选程序；程序完成后，还要将它改成其中一种。若把程序当作语言基本符号的线性串，并在同一层次将修改视为文本操作，那么每次修改，都必须在该语言可写出的所有程序——正确或错误的全部程序——这一全集中理解。难怪修改程序如此危险！

基本符号太小，也缺乏意义，不适合用来描述修改。珍珠体现独立设计决定，或者原问题陈述中一个隔离出的方面，其目的就是成为这种修改的自然单位。

换一种表述：ALGOL 60 诞生时，人们发现语法是表达程序文本结构的强大手段。语法受到如此推崇，以至许多同行把计算科学等同于语法分析！然而，人们稍稍忽略了：通过语法表达结构，结构只被十分间接地给出，必须对线性基本符号序列施加语法分析算法，才能导出。

意识到许多修改不影响大部分结构时，这就令人难受：费力地重新分析修改后的文本，最后同样的结构又出现了！我强烈感到，使用上下文无关方法表示结构的适用性，被严重高估了。

我身边有人给我看过这样一个 ALGOL 60 程序错误：一个程序在具备完整检查能力的实现上产生错误输出。该实现还要求，在程序最后一个 end 后，必须有最终的 progend；此附加符号在其他位置都不允许，以便确认 begin-end 配对正确。结果发现：

1. 程序某处漏了字符串的右引号。
2. 后面另一处漏了字符串的左引号。
3. 所得程序的 begin-end 结构在语法上正确。
4. 在两处遗漏之间声明的标识符，也只在这两处之间使用，因此连依赖上下文的检查也无法报警。

我原本就怀疑上下文无关方法是否足以表达宏观结构；见到这个错误时，竟很高兴！

越思考珍珠，越觉得：如果承认有责任为一个大型程序考虑例如一千种可能版本，那么类似珍珠的东西就是唯一出路。不能期望程序员把这一千个版本彼此独立地从头编写。

我能看到的唯一方法是组合技术：例如，造 250 颗珍珠，超过一条项链所需的 200 颗，再按特定选择串成项链。我看不到其他可行办法。另一种通过组合产生大量变化的机制是排列，但这里不能使用：最终必须是匹配的项链；给定珍珠后，能串成匹配项链的次序已经相当确定。而且，即使不唯一，允许的换序也基本无关紧要！

### 13.2 接口与概念的有效范围

珍珠还赋予只含项链上半部的“不完整”程序一个明确地位：它可以视为由适当机器执行的完整程序，而下半部给出这一机器的可行实现。因此，上半部的正确性可以不依赖下半部的具体选择而确立。

在相邻珍珠之间，可以作一个“切口”。它是一份机器手册：切口下方的项链提供该机器，切口上方所表示的程序使用它。手册是两部分之间的接口。我们觉得，这种接口比把数据表示看作操作之间接口的方式更有帮助，尤其有助于保证程序调整所需的组合自由。

还要谈概念沿项链的有效范围。例如，image 在最上面的 COMPFIRST 中引入，在倒数第二颗 LINER 中通过解释被消解。如果认定所设想程序需要太多存储空间，无法容纳 image，那么就必须作重大修改：用其他珍珠替换最上面五颗，因为它们就是 image 概念的有效范围！但底部珍珠，无论 LONGREP 还是 SHORTREP，都可以保留。此例说明，珍珠替换绝不限于底部。

关于概念的有效范围，有一项观察，第一次作出时令我十分激动。回头看相当显然，恰因此，值得明确说出。每颗珍珠对应“一个独立设计决定”，珍珠次序也就意味着决定的次序。能改变这一次序吗？能，但会得到不同的珍珠。

作为实验，我遵循一条熟悉建议：面对两个基本操作，这里是 build 与 print，立即决定它们的接口，这里是 image，以便二者独立细化。我照做，得到以下项链：

```text
COMPFIRST
LINER′
CLEARFIRST′
ISCANNER′
COMPPOS′
SHORTREP
```

中间四颗加撇号，表示它们虽然体现原来相同的决定，却是不同的珍珠。所得程序杂乱得多。为什么？

沿项链，可以标出每个概念的有效范围。它们当然重叠；可以把它们看作编织整个解释的单根线，组成一条“逻辑绳索”。杂乱版本的逻辑绳索由更多、且有时更长的线编成；绳索更粗，整个构造的相互牵连更紧密。

这项观察令我激动，因为它至少对我非常有说服力地表明：优雅、清晰等等确实具有显著的数量因素。莫扎特就知道这一点：他许多令人屏息的作品，简单得让人误判，仿佛几乎什么材料也没用就作成了！

### 13.3 推迟表示决定带来的好处

更技术地说，加撇号的版本杂乱，是因为过早把 image 解释为行，迫使 CLEARFIRST、ISCANNER、COMPPOS 都用行来解释；而本来还可以用图像来解释它们，也就是独立于具体表示。

换句话说，原版本比加撇号版本更审慎地利用了抽象能力。独立于具体表示的珍珠越多，程序就越容易调整，也越容易理解，因为那组珍珠可以在更高抽象层次理解。

这一经验似乎使可适应性和清晰性的目标获得了某些实质内容；更进一步，二者本质上相辅相成。这很令人鼓舞，虽并不令人惊讶。

这也至少让我更清楚地看到当前努力的范围。无论发展出什么，都不会成为一个通用问题求解器；既不是机械的，也不是写给人类问题求解者的那种。不过，当人成功找到解法时，它或许能帮助理解解法“优雅”的不同方面；因此，也可能提供某种指导。

## 十四、论分组与顺序安排

我们正在考虑一种明确承认抽象层次体系的程序设计工具，但本节也适用于当今意义上的程序设计语言，即在固定语义层次上的程序设计。本节很可能还对程序设计以外有所启示，因为它似乎涉及一般的问题求解。

我用两个例子说明，二者也都用于口试。第一个例子来自 Niklaus Wirth。

### 14.1 不含相邻重复子串的序列

要求构造程序，生成由 0、1、2 组成的非空序列，其中不得含有两个非空、逐元素相等、相邻的子序列。按字典序生成这些序列，直到生成一个长度为 100，即 100 位数字的序列为止。程序员可以利用已知事实：确实存在满足条件的长度 100 序列。要生成的序列开头为：

```text
0
01
010
0102
01020
010201
0102010
0102012
…
```

除第一个外，每个解都是在某个较早解上扩展一位得到的，因此算法是直接的回溯算法。

我们寻找“合格”序列，假定有一个基本操作可检查试探序列是否合格。若合格，就打印并在末尾加一个零，得到下个试探序列；若不合格，就执行“增进”操作：删除末尾所有等于 2 的数字，再将最后剩下的一位加一。

“末尾加零”与“增进”保证试探序列按字典序生成；解是其中选出的部分，所以也按字典序打印。开始检查的试探序列如下，星号标出的会因不合格而舍弃：

```text
  0
* 00
  01
  010
* 0100
* 0101
  0102
  01020
* 010200
  010201
  0102010
* 01020100
* 01020101
* 01020102
* 0102011
  0102012
  …
```

我发现，多数学生倾向于以下结构：

```text
将试探序列设为单个零;
repeat
    if 合格 then
        begin 打印试探序列; 在试探序列末尾加零 end
    else
        增进试探序列
until 长度 = 101
```

虽然按此思路写的程序输出正确，但可以提出异议，而且按我的看法应当提出。

第一，终止判据有问题：打印一个长度 100 的解后，我们知道算法，能推断再往后试探序列将第一次达到长度 101，于是将它用作终止条件；但这是十分间接、曲折的做法。有些学生没注意到生成了一个不必要的试探序列，把数组声明为 100 元素而非 101 元素，这清楚说明推理有多曲折。

第二，“增进试探序列”从不增加长度；每次舍弃试探序列之后，却多作一次长度检查。

我把此例用于考试时，课堂上还没有十分明确地强调问题求解原则，所以失望并不严重。在某种意义上，我庆幸观察到这些考试，因为这推动我尽可能寻找、表述并教授问题求解原则。

避免上述问题的程序，将空序列视为一个不打印的虚拟解。在相同细节层次上，其结构是：

```text
将试探序列设为空;
repeat
    在试探序列末尾加零;
    while 不合格 do 增进试探序列;
    打印试探序列
until 长度 = 100
```

这里，长度指已打印解的长度，如果已有打印的话；因而避免了关于终止判据的曲折推理。也不会生成一个最后永不检查的多余试探序列。由于两个循环嵌套，不再有多余长度检查。

以效率为主要标准的人，可能最认同最后一点。我自己很重视可理解性，因此更喜欢后一个程序：它可解释为以下结构的进一步细化。

```text
将序列设为空;
repeat
    将序列变换为下一个解;
    打印序列
until 长度 = 100
```

这个更抽象的程序只关心作为解的序列。在这一描述层次，可忽略从一个解到下个解的过程中，还会经过一连串失败的试探序列。

### 14.2 至少有两种幂和分解的最小数

第二个例子来自 Joe Weizenbaum。给定正整数 n，编写程序求最小的 s，使 s 至少能够以两种非平凡不同的方式，分解为两个 n 次幂之和。

例如：

$$n=1:\quad s=2=0^1+2^1=1^1+1^1.$$

$$n=2:\quad s=25=0+5^2=3^2+4^2.$$

$$n=3:\quad s=1729=1^3+12^3=9^3+10^3.$$

$$n=4:\quad s=635318657=59^4+158^4=133^4+134^4.$$

> **译注**：按例子，两底数取非负整数；“非平凡不同”排除仅交换两加数次序造成的区别。

首次在口试中使用此例时，学生花了二十分钟才有些熟悉问题，然后勾画出一个搜索算法。修补后，它确实能找到具有多种分解的数，却不能证明产出的 s 最小。事实上，他当时一直忽略了这部分要求。

于是他重整思路，写出如下形式：

```text
integer s, k;
s ≔ 1;
repeat
    s ≔ s + 1;
    k ≔ “s 可分解为两个 n 次幂之和的方式数”
until k > 1
```

这样得到的算法，效率低得无可救药。他的错误是过早决定按自然数次序逐一检查；其中绝大多数根本不能分解。

如果这样推理：所找的是满足附加性质的最小可分解数，就会得到初稿如下的算法：

```text
integer k, s, t;
t ≔ 1; 以及其他初始化;
repeat
    s ≔ “大于 t 的最小可分解值”;
    k ≔ “取得上述最小值的方式数”;
    t ≔ s
until k > 1
```

存储一组三元组——数对及其相应 s 值——保证每次其中都包含 s 值大于 t 且最小的数对，并在每次增大 t 时调整集合，就得到效率高出几个数量级的程序：t 从一个可分解值直接跳到下一个。

程序设计——或者一般的问题求解？——就是审慎地推迟决定和承诺！
