# 十二、逐步构造程序的第二个例子

程序结构作为分层机器体系的图景逐渐显现，我已经跃跃欲试，想拿它再编一个程序。这里使用的记法不应视为经过周密考虑的建议：它们只是按我的兴致选择，是实验的一部分。

## 12.1 问题：用行式打印机绘图

有一台行式打印机，由两条命令控制。`NLCR`（New Line Carriage Return，换行回车）把下一行最左端位置设为“当前可打印位置”；`PRSYM(n)` 在当前可打印位置打印由整数参数 n 指定的字符，再把其右邻位置设为新的当前可打印位置。为讨论方便，可允许行长无限。

只使用 n 的两个具体值，分别称为 `space` 和 `mark`。`PRSYM(space)` 让当前位置保持空白；`PRSYM(mark)` 打印一个给定可见字符，例如某种星号。

另给定两个以整数为自变量、取整数值的函数，满足：

$$0\le i<1000\quad\Longrightarrow\quad0\le fx(i)<100,\quad0\le fy(i)<50.$$

要求编写程序打印 50 行。从上到下，y 坐标依次为 49 到 0；每行从左到右，x 坐标为 0 到 99。对于某个满足 0 ≤ i < 1000 的 i，若某位置有：

$$x=fx(i),\qquad y=fy(i),$$

就在该位置打印标记，共一千个位置，若重合则更少；其余位置保持空白。也就是说，曲线以离散参数形式给定，我们要把行式打印机当作数字绘图仪使用。

我在口试中广泛使用这一问题。大多数学生很快发现：没有 `OLCR`（Old Line Carriage Return，返回原行行首）和“退格”，可打印位置的处理顺序由打印命令规定；这个顺序又与按 i 递增排列的标记顺序毫无关系。

于是，他们很快得出结论：似乎应使用存储器。先扫描一千个 i 值，以方便的方式存下页面图像；再在该图像控制下打印。更精确地说，假定计算机有足够存储空间，而 fx(i)、fy(i) 的计算可能很耗时，因此希望每个 i 只计算一次。

## 12.2 COMPFIRST：先构造图像，再打印

将这一设计决定记录如下：

```text
COMPFIRST
begin
    draw: {build; print};
    var image;
    instr build(image), print(image)
end
```

这段文档视为最终程序的组成部分，解释如下。

它针对名为 COMPFIRST 的机器。机器名用大写，尽量表达该机器程序所反映的决定类型。

接下来给出有名称的算法 draw，假定它是整个待构造绘图程序的名字。算法表示两个动作的所需时间顺序：先在存储器中构造图像，再按已存的值在纸上打印。

最后两行是声明或声明头部，命名运行上述算法所需机器的部件。image 是容纳页面图像的数据结构；它是该机器状态空间的唯一组成部分。指令集包含 build 和 print 两条指令。

继续前，需要指出两个缩写，我尚不知道它们是很明智还是很愚蠢。它们都源于：image 是该类型的唯一变量。

如果状态空间要包含两个图像，我会写：

```text
type image;
image var image1, image2
```

表示两个变量 image1、image2 具有相同的可能值集合；这一集合由名为 image 的**类型**刻画。以后详细说明 image 类型时，对两个变量都适用。

由于此类型变量只有一个，我冒险不区分集合及其唯一元素，二者都称 image。在 COMPFIRST 的描述中，如 `build(image)`，image 指变量；以后给结构细节时，它指类型。

最后一行的指令声明类似过程头部。通常，它们包含参数类型，而调用包含作为实参的变量。但若类型唯一决定了参数，这样区分似乎没有意义；所以我在声明里写实参，却在 draw 的算法代码中省略 image。于是，显式实参记法可留给确实使用组合选择自由的情形。

我想强调：名为 draw 的小算法，可以而且应当看作针对一台机器写的程序。应为这台机器写手册，说明：

1. build 给 image 赋值，使之表示由 fx、fy 指定、应在纸上打印的图像。
2. print 按 image 当前值所规定的图像，在纸上打印。

考虑 draw 的其他算法，或许最容易看出它确实是机器程序：

```text
draw: {print; build}
```

这是错的，因为此时 print 动作未定义。

```text
draw: {build; build; print}
```

正确，但多耗时间：第二次 build 赋给 image 的值，就是它已有的值。

```text
draw: {build; print; print}
```

则有意义，会把图像打印两次。

回到任务。如果有 COMPFIRST，draw 就完成工作。为讨论起见，也为符合实际，假定没有这样按需要定制的机器。那么，下个与前任务相似的任务，就是造出这台机器。

假定了三个实体：build、print、image，前两个都引用后者。因此，进一步规定 image 会影响前两个；不进一步承诺 image 的结构，也很难细化 print。但 build 可以独立进一步细化，所以首先选它。

## 12.3 CLEARFIRST：先清空，再设置标记

必须描述 image 如何取得正确放置一千个标记的值。从整体看，这给一个先前值未定义的变量赋值。若预想逐个添加标记，那么添加下一个标记将是作用于 image 已定义值的动作。因此，把整个设置过程看作作用于已定义的空白页值，似乎很合适。

这个决定得到：

```text
CLEARFIRST
begin
    build: {clear; setmarks};
    instr clear(image), setmarks(image)
end
```

clear 将 image 设为五十行空白图像；setmarks 调整此初值，加入曲线的一千个或更少标记。

CLEARFIRST 同样允许其他程序：

```text
build: {clear}
```

有意义，但输出五十行空白。

```text
build: {setmarks; clear}
```

含有未定义操作。

```text
build: {clear; clear; setmarks}
```

含有多余操作。下面也一样：

```text
build: {clear; setmarks; setmarks}
```

第二次 setmarks 只添加已经存在的标记，不改变 image 的值。

**记法说明。** 用 clear、setmarks 解释 build 时不显式写 image，因为除非机器确实使用实参选择上的自由，否则不想在算法中使用实参记法。此外，build 只有一个参数，没有为形参引入单独标识符。这种缩写也可能很不明智。

## 12.4 ISCANNER 与 COMPPOS：遍历标记并求坐标

下一个无需进一步承诺就能作出的决定，是描述如何依次处理曲线的一千个标记。暂用如下写法：

```text
ISCANNER
begin integer i;
    setmarks: {i ≔ 0;
        while i < 1000 do {add mark; i plus 1}};
    instr add mark(i, image)
end
```

在理解这一算法时，假定机器的指令集中有 `add mark(i, image)`，按添加第 i 个标记的要求改变 image。算法规定处理次序，表明所有标记都恰好处理一次。

但这并非全部。还引入了新变量 i，算法调用一组引用它的动作：`i ≔ 0`、`i < 1000`、`i plus 1`。如果完全一致，似乎也应把它们与 add mark 一样列在底部，表示以后可能需进一步说明。我没有这样做，而是像对待 `while-do` 一样处理它们。从语言语义角度，这种单独对待隐含已理解类型 integer 的方式似乎不理想，也难以解释为什么 integer 与 image 的待遇不同：在这台机器中，二者都隐含已理解。

然而我确实这样做了。我一直为不存在的机器设计程序，然后说：“如果现在有一台具有所假定基本操作的机器，任务就完成了。”逻辑上正确，实际中却是个玩笑，因为我们很清楚，不可能假定有一台通用机器，其指令集如此贴合需求。

不应忽视，也不应佯装忽视，在后续设计中提供这些基本操作的责任。以这种特殊方式援引已理解的 integer 类型及其操作，是为了表达：这些能力虽必须以某种形式提供，但提供它们不在程序员的责任范围内，而且程序员接受其任何合理实现。

又剩下一个无需承诺其他基本操作就可细化的操作。须说明：处理第 i 个标记，如何转为处理页面中的一个位置。构造负责计算位置的机器：

```text
COMPPOS
begin integer x, y;
    add mark: {x ≔ fx(i); y ≔ fy(i); mark pos};
    instr mark pos(x, y, image)
end
```

mark pos 按在待打印图像的 (x, y) 位置增加标记的要求，改变 image 当前值。

**说明。** 此次细化明确假定，可按自变量的任意顺序计算 fx(i)、fy(i)。若这两千个函数值要从输入流中，按规定 i 顺序成对读取，则最后两台机器必须合并。

## 12.5 为什么可以推迟表示决定

现在，我看不出不承诺尚模糊的 image 类型结构就能继续细化的可能。它的值如何存储？必须组织 image 类型的变量，也就是选择其可能值的表示方式。

我在不同地方讲过这个程序的不同版本。值得指出：至少两次，部分听众到这里时已经深感不安。例如，他们认为我不能声称已完成部分的程序正确；他们反对我说 `draw: {build; print; print}` 会打印两次相同图像，因为在**造出** print 之前，我怎么知道它不会通过副作用改变 image？

答案当然是：print 必须做规定它做的事，不应做未规定的事。但还有更多反对意见：我未证明表示唯一；也许 print 只是偏函数，在 image 的某些可能值上未定义，等等。

我的回答是：这些关切虽合理，却应在合适时机处理，也就是在承诺一种表示时，而不是此前。方法的力量，显然正在于：这么多程序能够独立于 image 值的表示方式写下。迄今所做的，确实似乎是审慎地利用了抽象能力；这里抽去的是数据结构 image 的具体表示。

即使现在认定该决定 image 数据结构了，也不必一次完全承诺。面对如何组织变量的问题，可以逐步决定，就像前面的算法细化一样。

## 12.6 LINER：把图像表示为行数组

回想问题来源：PRSYM、NLCR 迫使计算从上到下逐行输出图像。试着用行数组组成图像，来反映这一事实。下一层如下：

```text
LINER
begin integer j;
    image: {array line[0:49]};
    print: {j ≔ 49;
        while j ≥ 0 do {lineprint(line[j]); j minus 1}};
    clear: {j ≔ 49;
        while j ≥ 0 do {lineclear(line[j]); j minus 1}};
    mark pos: {linemark(line[y])};
    type line;
    instr lineprint(line), lineclear(line), linemark(x, line)
end
```

> **译注**：原文 clear 的循环体开头误用左圆括号，此处统一为与右花括号匹配的左花括号。`linemark(line[y])` 沿用作者省略唯一确定参数 x 的实验记法。

倒数第二行引入 line 类型。回顾一下：类型是一组可以区分的值；此类型变量在任一时刻，可取其中一个值。第一行定义说明：image 类型由 50 个 line 类型元素组成，编号 0 到 49。由于只有一种类型由它组成，我们仍未引入新的标识符，不论这样明智与否。

print、clear、mark pos 原来是对 image 的操作，现在译成用行操作表达的算法。代码里的真正实参，指定是哪一行；描述末尾列出指令，说明动作作用于“一行”，给出了类型，但不是具体参数。

本层引入新特点。首先，数据类型的结构细化，如 image，与算法细化，如 print、clear、mark pos，被放在很相近的地位。此前，可把方法视为为“子程序化”建立纪律——请原谅读者容忍这个可怕术语！如今可见，这只概括了一半目标，因为我们也试图对数据结构应用类似技术。

其次，以前的机器只解释一个实体，即一条指令或一种数据类型，而 LINER 解释整组实体。关键是尽量每层对应一个独立设计决定。这里的决定，是从此用行来理解图像，因此所有直接处理图像的操作都要译成处理其各行的操作。

图像已通过解释被消解，只剩 line 这一不寻常类型需要处理。下一层就做这件事。请注意：下一层只处理行；行被用来组成图像，已经无关紧要！

## 12.7 LONGREP：用字符数组表示一行

表示一行有许多可能，例如：列出应打印标记位置的 x 坐标，可按递增顺序排序；用 100 元素的布尔数组表示相应位置是否应有标记；或用 100 元素的整数数组，每元素保存对应位置 PRSYM 参数值 mark 或 space。

最后一种便于扩展：可以在同一图像中打印以不同标记表示的不同曲线，所以选它。得到：

```text
LONGREP
begin integer k;
    line: {integer array sym[0:99]};
    lineprint: {k ≔ 0;
        while k < 100 do {PRSYM(sym[k]); k plus 1};
        NLCR};
    lineclear: {k ≔ 0;
        while k < 100 do {sym[k] ≔ space; k plus 1}};
    linemark: {sym[x] ≔ mark}
end
```

但这一实现会用空格填满最右标记右边的余下行长，就像写信要转到新段落时，却不停敲空格键直到铃响！

## 12.8 SHORTREP：只打印必要部分

下一版省去多余 PRSYM 命令，甚至让 line 变量中不必定义的元素保持未定义。每行关联一个计数器 f，表示该行所需 PRSYM 命令数。清空一行现在简化为把 f 置零！

```text
SHORTREP
begin integer k;
    line: {integer f; integer array sym[0:99]};
    lineprint: {k ≔ 0;
        while k < f do {PRSYM(sym[k]); k plus 1};
        NLCR};
    lineclear: {f ≔ 0};
    linemark: {sym[x] ≔ mark;
        if f ≤ x do {
            k ≔ f;
            while k < x do {sym[k] ≔ space; k plus 1};
            f ≔ x + 1}}
end
```

## 12.9 后补说明：让正确性更容易理解

上面的程序基本就是我向至少五组听众展示过的程序。两个月后的现在，我从容思考正确性证明时，突然意识到：给出的 linemark 算法暴露了我的旧习惯；与下面的备选方案相比，它是一段糟糕的代码：

```text
linemark: {
    while f ≤ x do {sym[f] ≔ space; f plus 1};
    sym[x] ≔ mark}
```

这一版本保证：每次执行 `sym[x] ≔ mark` 时，关系 `x < f` 总是成立；第一行的功能恰是确保这一点。请读者试着理解两版本并比较所需推理，随后就会同意我对原版的评价。

这个第二版本，源于以下观察。程序中的条件语句：

```text
if B do S
```

有两种用法。一种是执行 S 不会使 B 由真变假；另一种是保证执行 S 会使 B 由真变假。后一种情况下，条件语句的功能，是确保执行后 B 不成立。

于是，它本质上是以下循环的简写：

```text
while B do S
```

循环具有使 B 不再为真的性质，只要它终止。但要证明这种简写合理，须另行证明：循环体至多执行一次。在第八章 2b4(4) 层，我们写：

```text
while “ord 太小” do “将 ord 加一”
```

当时没有费心引入这种简写；其实那里用条件子句也能完成任务！
