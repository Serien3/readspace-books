# 五、论证明的有效性与实现的有效性

上一节假定了“精确无误的算术”。根据我的经验，这类证明的有效性常遭到质疑：人们认为，实际工作中永远没有精确无误的算术可用——允许的整数值通常有绝对上界，实数只能以有限精度表示，等等。那么，这些证明究竟有什么效力？

答案似乎如下：如果假定一个理想、完美的世界，并据此证明程序正确，就不该惊讶于这个理想程序在“不完美”的实现上执行时出问题。这是显然的！因此，若希望在更现实的世界里证明程序正确，就应从一开始承认：程序所调用的全部操作，尤其是算术操作，未必完美；但必须以近似公理化的方式，说明它们为使程序正确执行而应满足的性质，也就是正确性证明所依赖的性质。上一节例子中，这一要求就是在区间 [0, 2a] 内进行精确的整数算术。

> **译注**：作者的区间表述在 a = 0 或 d > 2a 时未覆盖初始化值 d。若要求所有出现的整数均可表示，统一的充分范围可写为 `[0, max(d, 2a)]`。正文保留作者的表述，以区分原文与校订意见。

编写对实数进行舍入运算的程序时，必须清楚自己所作的假设，例如：

```text
b > 0 蕴含 a + b ≥ a
a * b = b * a
-(a * b) = (-a) * b
0 * x = 0
0 + x = x
1 * x = x
……
```

这些关系成立，往往对程序逻辑至关重要。为了兼容性，程序员最好尽量少提要求；而好的实现应当满足尽可能多的合理要求。

这里适合坦白我的一个失误。在实现 ALGOL 60 时，我们决定：`x = y` 不仅在精确相等时返回 `true`，也在两值只差所表示的最低有效位时返回 `true`，否则算出 `true` 的可能性实在太小。我们当时想到的是收敛迭代：它可能在舍入精度范围内来回振荡。

我们出于好意，宽松地认定实数相等，但很快发现，所选操作的性质弱到几乎没有用处。归根到底，即使已经确认 `a = b and b = c` 为真，程序员仍不能断定 `a = c` 为真。这个决定很快就改了。

正是这次经历让我明白：程序员能够使用工具，完全有赖于工具所具有的某些性质；反过来，程序员必须能够说明自己需要哪些性质。通常程序员并不这样做，因为关于哪些性质可视为理所当然，尚无传统可循；因此，这会要求比一般情况下适宜程度更高的明确性。劣质浮点硬件机器的泛滥，加上“自动计算机主要是数值分析人员的工具”这一误解，对这门职业造成了很大伤害！
