# 三、论辅助思考的工具

上一节说，程序员有义务让自己的产品具有“有助于推理的结构”；我们又把程序结构同令人信服地证明程序正确性联系起来。

然而，我们如何说服别人？如何说服自己？哪些典型思维模式使我们能够理解？本节将概览这些问题。我向专业心理学家诚挚致歉，因为这里的讨论难免外行而肤浅。不过，我希望，也相信，它足以提供一个尺度，用来衡量某种拟议结构的用处。

在帮助我们理解程序或其正确性证明的工具中，我想特别指出三种：

1. 枚举；
2. 数学归纳法；
3. 抽象。

## 3.1 枚举

在我看来，若要验证按顺序执行的一组列举出来的语句所引发的计算具有什么性质，就要诉诸枚举；其中包括区分两种或更多情形的条件子句。下面给出一个“枚举推理”的简单例子。

要求证明：对变量 `r` 和 `dd` 顺序执行以下两条语句，会保持关系式 (1) 不变。

```text
dd ≔ dd / 2;
if dd ≤ r do r ≔ r - dd
```

$$0 \le r < dd. \tag{1}$$

只需“跟着”这一小段程序走，假定开始时 (1) 成立。第一条语句把 `dd` 减半而保持 `r` 不变，执行后便有：

$$0 \le r < 2 \times dd. \tag{2}$$

现在区分两种互斥的情形。

**情形 1：`dd ≤ r`。** 结合 (2)，得到：

$$dd \le r < 2 \times dd. \tag{3}$$

此时执行 `do` 后的语句，使 `r` 减去 `dd`。由 (3) 得到最终 `0 ≤ r < dd`，即 (1) 成立。

**情形 2：`non dd ≤ r`，即 `dd > r`。** 此时跳过 `do` 后的语句，`r` 也已达到最终值。`dd > r` 与第一条语句执行后成立的 (2) 结合，立即得到 `0 ≤ r < dd`，所以在第二种情形下，(1) 同样成立。

这样，我们既完成了关系式 (1) 不变性的证明，也完成了一个包含条件子句的枚举推理实例。

## 3.2 数学归纳法

我特别提到数学归纳法，因为据我所知，它是唯一最终能让我们处理循环——例如由重复子句表达的循环——以及递归过程的推理模式。下面举一个例子。

考虑值序列：

$$d_0,d_1,d_2,d_3,\ldots \tag{1}$$

其定义为：

$$d_0=D, \tag{2a}$$

$$d_i=f(d_{i-1}),\quad i>0. \tag{2b}$$

> **译注**：所据文本在 (2b) 中写作 `i > 1`，这会使 `d₁` 没有定义；依据后续推理校订为 `i > 0`。

D 是给定值，f 是给定的可计算函数。要求使变量 `d` 等于序列中第一个满足给定可计算条件 `prop` 的值 dₖ。已知这样的值存在，且 k 有限。更正式地说，要求建立：

$$d=d_k, \tag{3}$$

其中 k 由下列条件确定：

$$\operatorname{prop}(d_k), \tag{4}$$

$$\neg\operatorname{prop}(d_i),\quad 0\le i<k. \tag{5}$$

考虑以下程序片段：

```text
d ≔ D;
while non prop(d) do d ≔ f(d)
```

上式记为程序 (6)。第一行是初始化，第二行是循环，由含义应当不言自明的重复子句 `while … do …` 控制。借用上个例子的条件子句 `if … do …`，可以更正式地说明其语义：

```text
while B do S
```

与下式语义等价：

```text
if B do
    begin S; while B do S end
```

这意味着，`non B` 是循环终止的充分必要条件。

将 `while B do S` 中的 S 称作“被重复执行的语句”。我们要证明，在程序 (6) 中，第 n 次执行这条语句后，对 n ≥ 0，有：

$$d=d_n, \tag{7a}$$

$$\neg\operatorname{prop}(d_i),\quad 0\le i<n. \tag{7b}$$

上述断言在 n = 0 时成立，这可以用枚举推理说明。接下来，也用枚举推理证明：若它对 n = N（N ≥ 0）成立，则对 n = N + 1 也成立。

第 N 次执行之后，(7a)、(7b) 对 n = N 成立。第 N + 1 次执行发生的充分必要条件是 `non prop(d)` 为真。由于 (7a) 给出 d = d_N，这意味着 `non prop(d_N)`，从而 (7b) 对 n = N + 1 成立。另一方面，d = d_N 与 (2b) 给出 f(d) = d_{N+1}。因此，第 N + 1 次执行 `d ≔ f(d)` 的净效果是建立 d = d_{N+1}，也就是 (7a) 对 n = N + 1 成立。归纳步骤至此得证。

现在证明，循环在第 k 次执行后终止。不可能发生 n > k 的第 n 次执行，因为按 (7b)，这会意味着 `non prop(dₖ)`，与 (4) 冲突。若循环在第 n 次执行后终止，则终止的充分必要条件 `non (non prop(d))`，结合 (7a)，成为：

$$\operatorname{prop}(d_n). \tag{8}$$

这又排除了 n < k 时终止的可能，否则会违反 (5)。因此，循环恰在 n = k 时终止；(3) 由 (7a) 得到，(4) 由 (8) 得到，(5) 由 (7b) 得到。证明结束。

在结束这个说明数学归纳法如何用于推理的例子之前，我还想说几句话。我不安地感觉到，有些读者——尤其是经验丰富、能力出众的程序员——此刻一定很恼火。他们认为程序 (6) 的正确性显而易见，因此不明白为何要如此大费周章：“谁都知道，满足条件的第一个序列值是什么意思，为什么要像 (3)、(4)、(5) 那样郑重其事地重述问题？难道他真指望我们这些有工作要做的人，每写这么简单的一个循环，就附上如此冗长、满是数学装饰的证明？”诸如此类。

说实话，上面证明的繁琐和冗长，也令我恼火！但目前，如果认真证明这一程序的正确性，我还做不到好多少。有时，这使我想起多年前对平面几何最初几个简单定理所作的那些令人抓狂的证明：被证明的事情，与欧几里得公理本身一样“显而易见”。

当然，我不敢建议——至少现在不敢——程序员每写一个简单循环，都有义务提供这种证明。倘若如此，他就根本写不出有任何规模的程序！这与把每个平面几何证明都明确、完整地还原到欧几里得公理一样不切实际。参见第一章。

我要表达的有三点。

第一，程序员之所以觉得 (6) 这样的构造显然正确，是因为熟悉它。我更愿意把这种行为看作无意识地援引一个他**知道**的定理，尽管他也许从未费心将它表述出来。他一生中曾经确信它为真，尽管可能已经忘记当初如何确信，而且那种方式多半不适合付印。不过，我们可以把关于程序 (6) 的断言称为“线性搜索定理”；知道这个名称，便更容易、更自然地有意识援引它。

第二，据我所知，还没有一套像上例那样、其用处得到普遍认可的定理。但这并不奇怪：这种定理体系的缺失，直接源于其研究对象——程序——尚未定型。程序员处理的对象，远没有平面几何的对象那样确定。在此期间，凭直觉就能胜任的程序员，很可能是这样的人：只要可行，就把自己限制在非常熟悉的程序结构之内；一旦构造对自己而言不寻常的东西，就变得十分警觉、谨慎。不过，对于一种已经确立的程序设计风格，寻找适用于这类程序的定理体系，可能很有价值。

第三，上个例子所需证明的长度，是不应忽视的警告。当然，也许更好的数学家能够做出短得多、更优雅的证明。就我个人而言，我更倾向于据此认定：程序设计比人们通常以为的更困难。让我们诚实地保持谦逊，把证明的长度视为一项迫切的忠告：尽可能限于简单结构，以智力上的谦逊，像躲避瘟疫一样避开“巧妙的构造”。

## 3.3 抽象

此时，我很难十分明确地说明抽象的作用，部分原因是它贯穿整个主题。考虑一个算法，以及它可能引发的一切计算过程：从这些计算过程中抽去每次所操纵的具体值，剩下的就是算法。“变量”这个概念，代表着对其当前值的抽象。

有人曾对我说——很遗憾，我记不起是谁，无法给予应有的致谢——一个人一旦理解程序设计中使用变量的方式，就理解了程序设计的精髓。回到刚才关于循环的数学归纳法，可以确认这一说法：一方面，通过抽象引入概念，才能用这些概念表述归纳步骤；另一方面，真正使“变量”概念成为必要的，正是重复执行。（没有重复执行时，只需使用“量”：其值至多定义一次，无须像变量那样重新定义。）

给一个操作命名，然后只根据“它做什么”来使用它，完全不考虑“它怎样工作”，同样包含抽象。（同样，我们应说，程序设计手册描述的是一台抽象机器；制造商交付的具体硬件，只是这一抽象机器的机械模型，而且通常并不完美！）在程序里使用一个有名称的操作而不管它怎样工作，与使用一个定理而不管它如何证明，有很强的相似性。即使证明极其复杂，定理本身仍可能十分方便！

这里，我再次提醒我们能力的局限。枚举推理在它所能覆盖的范围内很好，但我们思维迟缓，它覆盖不了很远。只有在严格的限制条件下——十分节制地使用它——枚举推理才是合适的思考工具。我们应当把抽象视为减轻枚举推理负担的主要思维技术。

英国泰丁顿国家物理实验室的 Mike Woodger 在此提出了下面的意见。我怀着感谢将其收入：“公理或定理用未经分析的术语来表述；一个有名称的操作，则预期作用于未经分析的操作数。两者之间也有相应的类比。”
