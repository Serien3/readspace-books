# 十、论以存储空间换取计算速度

在当今的顺序计算机中——这里指 1969 年春——可以区分两个主要部件：主动部件处理器，以及被动部件存储器。前者的特定职责是快，后者的特定职责是大。下面假定，这种功能划分会持续足够久，值得研究它的后果。

从程序员角度看，存储空间与计算时间是两种不同资源。我认为分配它们、在二者间分担负荷，是程序员而非系统的责任之一。本节讨论这种责任的后果，不讨论估计各种负荷的技术，也不给出影响选择的定量判据，而讨论各备选方案之间的逻辑关系。

**说明。** 某些选择交给系统，并非不可想象。但除最简单的情况外，设计方案并确立等价性，似乎仍需程序员作出数学上的创造。自动化这种问题求解活动的努力，都不在本书范围内。

## 10.1 保存函数值与按需更新

最简单的情形是：计算经常需要 `FUN(arg)` 的值。FUN 是给定可计算函数，定义在一个或多个已存储变量的当前值上，这些变量统称 arg。版本 A 只存 arg，需要时计算 FUN(arg)。版本 B 引入额外变量 fun，其唯一目的，是记录与 arg 当前值对应的 FUN(arg)。

版本 A 中出现：

```text
arg ≔ …
```

即对 arg 赋值；版本 B 则出现：

```text
arg ≔ …; fun ≔ FUN(arg)
```

从而保持 `fun = FUN(arg)`。因此，凡 A 需要求 FUN(arg) 的地方，B 只需取 fun 的当前值。

偏好 B 可能有两个理由。第一，若读取 FUN(arg) 比对 arg 赋值更频繁，B 就可能少用计算时间。必要时，还可增加布尔变量“fun 已更新”，表示是否认为 `fun = FUN(arg)` 成立。对 arg 赋值时，同时：

```text
“fun 已更新” ≔ false
```

每次需要 FUN(arg)，先检查此变量，看是否必须重算；若须重算，把结果赋给 fun，并按含义将“fun 已更新”置为 true。称最后这个方案为版本 C。

三个程序仅在 A 对 arg 赋值或使用 FUN(arg) 的地方不同，显然就输出而言等价。用机械方式从 A 导出 B 或 C，也并非不可想象。

## 10.2 利用变化规律增量更新

但情形常没有这么简单。现在谈引入 fun 的第二个理由：对任意 arg 从头计算 FUN(arg)，往往很不合算；而在 arg 改变时计算 FUN(arg) 如何变化，却容易得多。此时，调整 fun 与函数依赖的性质之间的联系，比 `arg ≔ …; fun ≔ FUN(arg)` 所暗示的更紧密。

这种可能性不仅与函数依赖的性质密切相关，也常与计算推进时“变量 arg 的历史”相关。素数表程序引入 ord，就是一个鲜明的例子。ord 是依赖 j 的函数，是满足下式的最小值：

$$p[ord]^2>j.$$

正因为 j 随时间单调增加，调整 ord 才是很有吸引力的操作。

在我对程序的理解中，希望这类保存冗余信息的额外变量，能清楚地被认作额外变量；即使函数关系不是十分确定，例如同一例子中的 mult 表，也如此。我很倾向于将这样的程序看作更抽象程序的优化细化，即使额外变量实现的优化，对达到实际可接受性能必不可少。

从效率角度，这样的变量可能重要到令人觉得：设想一个抽去了它的层次，是不负责任的白日梦。操纵这些变量的方式，往往被体验为算法的主体；我们数学才智的成果也常在这里收获。

关键在于：虽然至少一种这种优化细化的可能性，对得到实际性能必不可少，但仔细观察，常会发现，即使在最粗略的层次上，它也远非唯一。

**说明。** 我记得有一个程序，额外信息冗余到不仅能从 arg 导出 fun，也能反过来导出 arg。二者关系突然变得对称，我便被一个问题严重困扰：我凭什么非对称地处理它们？

该程序生成某个组合谜题的所有解。仔细查看后发现，还存在第二个组合谜题，并能证明两个问题的解之间有一一对应。如果解决的是第二个问题，fun 与 arg 的角色就会互换！在传统程序设计中，这类函数依赖不明确显示，两谜题很可能由完全相同的程序解决；但我构造了两个结构不同的程序。

我认为这是正确的。因为用同一个程序解决两个谜题，需要的正确性证明随所解谜题而不同。若还要求程序结构反映对计算过程的理解，这种做法似乎就不太合理！
