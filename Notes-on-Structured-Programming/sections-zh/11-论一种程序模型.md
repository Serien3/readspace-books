# 十一、论一种程序模型

在拥有程序之前，必须先构造它；拥有之后，若编写它有意义，就会执行它。本节不着重讨论构造和执行活动，而试着把程序视为静态对象。我们希望它是高度结构化的对象，主要问题是：设想什么结构，为什么？希望最终得到既方便构造又方便执行的程序结构。

当然，我在思考时不可能忽略这两个过程，但目前不想讨论它们；尤其不讨论设计方法——从外向内还是反过来——也不讨论实现上的后果。仍为避免过分复杂，只讨论顺序程序。

如果只评判程序本身，我的中心想法是：希望程序按我能够理解的方式写下，按我愿意向别人解释它的方式写下。不过，不再限定的话，这只是人人赞成的空泛主张。让我尝试具体一点。

## 11.1 从区域注释到抽象指令

考虑一个非常简单的计算，可分辨出三个依次发生的动作：输入数据、处理数据——即计算本身——输出结果。一种程序表示是长串语句：

```text
begin
    …
    …
    …
    …
    …
    …
end
```

再进一步，为解释加些标号：

```text
begin
    输入开始：…
              …
    处理开始：…
              …
    输出开始：…
              …
end
```

读文本时，这些标号提示接下来发生什么。更好一些，可以写：

```text
begin
    输入：begin …
                … end;
    处理：begin …
                … end;
    输出：begin …
                … end
end
```

此时，把标号与其说看作程序文本中某个点的标记，不如看作其后 `begin-end` 所界定区域的名称，或者看作计算所分解成的三个动作的名称。

但即使这样，它们仍然只是注释，是给有兴趣的人类读者的解释性附加文字；我却希望它们成为程序不可分割的一部分。希望程序文本在某处明确反映：无论进一步查看时三个动作是什么形式，计算已分解为它们依次发生。

一种办法，是在某处写下三个抽象语句的文本序列：

```text
输入; 处理; 输出
```

约定：这三个动作的时间顺序确由上述文本顺序控制，而进一步细化写在“别处”，也许分开写，但肯定不规定相对次序。

如果闭式子程序不是二十多年前就已发明，现在便是发明它的时候！也就是说，我们又回到熟悉的领域，以致许多读者会觉得上当。我却不这样想：只要经过验证的方法仍令人满意，坚持它就不该羞愧。但应清楚知道，希望从它得到哪些好处；必要时调整它，最后为使用它建立纪律。所以让我回顾子程序概念，因为过去一年，我对它的评价改变了。

## 11.2 子程序、过程与局部变量

我最初通过 EDSAC 接触闭式子程序概念，参见本章末尾的参考文献。子程序是标准程序库的基础。那时构造硬件本身是巨大冒险；许多标准例程，是以稀缺的存储空间和计算时间换取电路的手段。例如，指令集中没有除法指令，就提供除法子程序。

奇怪的是，我不记得当时曾把子程序理解为将给定机器“重建”为更合适机器的手段；也不记得主要把它看作用户为反映自己的分析而构思、构造的对象。它们更多是供用户使用的标准例程。后来，我主要把它们看作缩短程序长度的手段。

但整个程序仍被构思为在单一、均匀的存储器中活动，在没有结构的状态空间中活动；整个计算仍被构思为一个处理器执行的单一顺序过程。以后几年，我在许多程序设计课中忠实宣讲这一套，常解释调用序列如何传递返回地址，子程序又如何在开始时设置自己末尾的“链接”，即返回跳转。

现在，我更愿意认为主程序有自己的指令计数器：子程序执行完后，它继续“计数”；绝不把其“休眠中的值”视为传给子程序的参数。

然而，旧观点已经进入许多机器的硬件。有些机器的子程序跳转把链接存入子程序的“零号地址”，从“一号地址”继续取指，这使可重入代码和递归子程序较难实现。甚至在本十年里，有些机器在程序中断时，仍把被中断程序的“程序状态”存到与中断相关的位置，而非与被中断程序相关的位置！

十年后，ALGOL 60 出现，局面改变了；我们不再叫它闭式子程序，而叫“过程”。程序员仍视它为缩短程序文本的方便手段；越来越多的人也开始用它组织结构，使针对预见到的规格变化的调整，只需替换一个或几个过程体，或者改变调用的若干实参。但最主要的新东西，是局部变量概念。

它体现在两个重要方面。

第一是**作用域**：不是所有变量在整个程序中都同样可访问。过程的局部变量在过程体外不可访问，因为在外部它们无关紧要。过程为完成自己的任务需要什么局部变量，是其私事，不关调用它的主程序的事。主程序能够，而且**必须**独立于这些局部变量来构思；这一事实得到了审慎的反映。我们可以对 ALGOL 60 的具体作用域规则有所疑虑，但应承认，它是朝正确方向迈出的重要一步。

第二，过程可以递归使用；更精确地说，允许直接或间接调用自身。关于这种能力的好处，曾有许多激烈争论；据我所见，讨论已经平息。反对递归过程的理由始终是效率：不可重入代码能执行得快得多。

但多道程序设计的出现，又带来了灵活分配存储空间的需求。若仍有机器执行不可重入代码明显更快，即对递归例程施加过重代价，我冒昧地认为，它的结构如今应被称为有些过时。

递归过程迫使我们承认：静态的过程文本，与动态的激活——有人称为它的一次“化身”——不同。过程文本是一回事，这一次所操作的局部变量集合，是另一回事。

## 11.3 过程概念的局限

到这里都很好。现在说不足，无论称作语言上的还是概念上的都可以。

局部变量在进入过程时“创建”，退出时“消灭”。正是对某次过程激活所属变量生命期的这种自动控制，使我们能用栈，即后进先出的存储安排，实现递归过程。局部变量只在所属激活期间存在，这使过程无法在幕后把信息从一次激活传给下一次。

为克服这一点，引入了 `own` 概念，但它没有解决问题。一方面，递归情况下 `own` 变量到底适合做什么，很不清楚；另一方面，不能编写一组共享若干 `own` 变量的过程。可以把变量声明在包含过程声明的外层块里来模拟，但作用域规则会使它们过于广泛地可访问，不能再看作“幕后”的东西。

我们的结论——既非新观点，也绝非我一人的观点——是：ALGOL 60 的 `own` 概念考虑不周，必须寻找新的方式，控制并描述局部变量的生命期、可访问性与身份。

我对过程概念还有一个意见：它仍主要被看作缩短程序文本的手段，尽管递归时被缩短的文本长度可能未知。过程调用的语义用著名的“复制规则”描述：调用被理解为简写；从语义上，应以过程体文本的一份副本替换它，适当调整标识符并替换参数，再由执行主程序的同一机器执行修改后的文本。

于是，它仍是由单一顺序机器执行的一段程序文本，或其表示。而恰恰是这一单一机器的图景，现在已不能让我满意。

## 11.4 虚拟机器的分层层次

我希望把主程序看作由它自己的专用机器执行：该机器有合适的指令集，操作合适的变量，并在自身指令计数器控制下安排执行顺序。这样，若拥有这台机器，主程序就会解决我的问题。

之所以希望这样看，是因为它强调：不管这台机器——很可能仍是虚拟的——是否可用，都可以讨论并确立主程序的正确性。我不必拥有它，只需拥有与正确执行当前主程序相关的规格说明。

对我而言，构思虚拟机器体现了抽象能力。这与理解高级语言程序类似：无须知道乘法、下标访问等操作如何实现，也无须知道最终负责执行的硬件采用什么数制这样的无关细节。

实际中，这台理想机器当然往往不存在。于是，下个任务——在结构上类似原任务——是编程模拟“上层”机器。为此必须决定数据结构，为上层机器提供状态空间；还需构造一组算法，各自实现上层机器指令集所假定的一条指令。最后，“下层”机器可有为自身方便而引入的私有变量，完全不在上层机器的领域和作用域内。

但这一组程序所针对的机器，极可能也不存在。因此下个工作，又是用再下一层机器的程序模拟它，如此继续，直到得到硬件能够执行的程序。

若能沿此思路建立程序，就把它组织成了若干层。每一程序层都应能在假定有合适机器执行它的前提下独立理解；而每一层的功能，则是模拟紧邻上层所假定可用的机器。

为什么采用此模型？希望得到什么好处？试列如下：

1. 第八章的经验强烈表明：对应不同抽象层次的分层安排，是很有吸引力的程序构造载体。
2. 可以合理希望，许多程序修改可表述为用兼容的机器替换某台虚拟机器。
3. 希望它能帮助掌握运行中修改程序所产生的问题。如果某层机器停在两条指令之间，所有下层机器完全静止，可以替换；所有上层机器则应视为正处于某条指令的执行中，其状态仍在转换。顺序机器的状态只能在指令执行之间解释。若想随时判定哪些解释有效，那么每台机器都有自己指令计数器、各自“数自己的指令”的层次图景，更有用。通常语言以同一种尺度，例如单条语句的“粒度”，衡量计算进展；此时面对“哪些解释何时有效”的问题，我就有些无从着手。
4. 希望模型还能帮助处理检测到故障后的全部或局部恢复问题。我最近参与设计、构造一个多道程序系统；最恼人的事之一，是某个存储单元发出奇偶校验报警时，我们完全无法用机械方式估计灾难范围。唯一能实现的安全反应，是立即停止整台机器；这实在不是值得自豪的方案！
5. 分层机器的层次图景，能抑制无节制使用“分而治之”的一种危险：各部件编写得过于独立，造成重复劳动，甚至更糟。某层含有由某台概念机器执行的“一组程序”，这强调同组程序应共享相同的基本操作。分工是好事，但另一方面，还必须把分散的线头重新接起来！
